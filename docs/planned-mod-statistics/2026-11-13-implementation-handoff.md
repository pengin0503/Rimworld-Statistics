# Planned MOD statistics implementation plan

> **For implementers:** Use superpowers:executing-plans. Each numbered task can be built and reviewed independently after Task 0.

**Goal** — Add player-facing, cross-colony lifetime statistics for confirmed outcomes from optional MODs in RimWorld 1.7.

**Architecture** — One package uses the existing optional provider registry, live accumulator, checkpoint, cross-colony aggregation and UI. Bind the loaded optional methods once at startup and count validated gameplay transitions on the game thread. Use one VEF processing hook for both content owners and preserve their separate metric identities.

**Tech stack** — C#/.NET 10, Harmony, RimWorld 1.7, existing Rimworld-Statistics Core and provider registry.

**Scope and inputs** — [Master register](README.md), [35-candidate disposition](2026-11-13-candidate-disposition.md), [pinned upstream references](2026-11-13-reference-lock.md). Base is main `a0008f4`. Start with Tasks 1–15 in order after the shared wiring. The order uses the existing reach evidence for confirmed slices, with the less-established reach targets toward the end. Each task implements only its defined outcomes. Conditional rows retain their explicit proof steps and can be scheduled as soon as the relevant evidence is available.

## Global constraints

- Use the selected DLL, PackageId and declaring type/signature from the lock. Validate method/field shape and assembly ownership before registering the affected family. Use reflection/delegates bound once, guarded callbacks and only actual required DLC. Source/IL evidence here is from the pinned public trees. Real-game compatibility is a separate result.
- Use one checkpoint-based opt-in acquisition per family. Sum the representative observation of each independent colony through the existing aggregator. Same-colony saves and rewind branches must follow the existing checkpoint lineage. A missing, disabled, unsupported or interrupted target preserves prior data and coverage semantics.
- Keep descriptors Unverified and opt-in. No retrospective inference from current pawn records, stock, loaded lists or enabled-MOD metadata. Use EN/JA labels and descriptions that describe the exact event and unit. Historical display follows the existing experimental settings.
- Keep build references optional. Use no compile-time assembly reference to the observed MOD. Store only numbers, qualified Def keys and existing provider metadata. Never store pawn names, player identifiers, third-party files or attached saves in the repository.
- Save filtering and output packaging remain in the current pipeline. New live callbacks must return before reflection, allocations or collection traversal when their unit is closed. A task needs build/package evidence and reports in-game parity and performance separately where the 1.7 test host is usable.

## Review focus

| Risk | Owning test |
|---|---|
| A target is absent, disabled, mismatched or faults during installation | Task 0 verifies no active acquisition, isolates a failing patch and preserves saved values after removal |
| Prefix/postfix sees an unrelated action or a skipped original | Postfix-based tasks require `__runOriginal`; call-site wrappers preserve return values and exceptions. All tasks test false/no-op transitions; Task 2 also tests a blocked or partially emitted process |
| Same state is observed after load or through multiple scopes | Tasks 3, 4 and 6 check reused state and replay. Task 0 checks save/load, checkpoints and rewind branch selection |
| Repeated operations exhaust a per-event dedup dictionary | Task 0 records 4,097 confirmed transitions and requires 4,097 at the checkpoint. It separately exercises qualified breakdown-key overflow |
| Ownership or Def identity is ambiguous across MOD inventories | Tasks 0 and 2 test equal DefName from unrelated owners, unknown ownership and two packages with one framework hook |
