# External MOD statistics SDK — experimental 1.2

Status: **experimental / NOT compatibility-guaranteed**, pending target-game acceptance and performance testing. This document describes the current candidate code, not a release commitment.

## Integrated optional gameplay-MOD statistics (2026-11-11)

The Rimworld-Statistics host now embeds the previously separate Hospitality, Recruitment, Dubs Bad Hygiene and Smart Apparel Upgrade adapters. They use the **same backward-compatible SDK 1.x API and existing checkpoint/representative-save/profile store** as external providers, preserving all stable IDs and revisions. The host package ships **only** `RimworldStatistics.dll`, `RimworldStatistics.Core.dll` and `RimworldStatistics.Api.dll`; third-party target MOD assemblies and standalone statistics addon DLLs are **not bundled**. When a gameplay target is absent, no reflection/patching/collection runs. If its old standalone statistics addon remains installed during migration, that addon is allowed to own the corresponding hooks and the integrated implementation stands down until removal and restart.

Previously saved numbers remain visible after target or old addon removal; missing time intervals are not backfilled. The rest of this document remains the SDK contract for other third-party developers and is not deprecated by host integration.

## Host and binary distribution

The host MOD `pengin0503.rimworldstatistics` packages **one** `RimworldStatistics.Api.dll` inside `1.7/Assemblies`, together with its existing `RimworldStatistics.dll` and `RimworldStatistics.Core.dll`. The external consumer compiles against the API reference but **must not copy any API/Core/host DLL into its ZIP**. Assemblies are resolved from the host at runtime. Source-level project reference for local development:

```xml
<ProjectReference Include="../../Source/RimworldStatistics.Api/RimworldStatistics.Api.csproj" Private="false" />
```

For separate repositories, use a compile-time reference to the host's published `RimworldStatistics.Api.dll` with `Private="false"`, or a separately distributed reference package containing metadata only. Do not ship that DLL in the consumer.

An optional external MOD should use `<loadAfter><li>pengin0503.rimworldstatistics</li></loadAfter>` **without** `modDependencies`; its own startup code must probe loaded assemblies by name `RimworldStatistics.Api` **before** invoking any API-typed code. Use a no-inline nested bridge method with no API types in startup-class signatures. See `../../examples/StatisticsSdkSample/Source/SampleSdkClient.cs`. When the host is missing, registration and emission are skipped without warning/error. The sample is built independently.

## ABI and semantic version policy

- Assembly identity: `RimworldStatistics.Api`, `AssemblyVersion 1.0.0.0` (`FileVersion 1.2.0.0`); the 1.x ABI is additive only so external consumers compiled against 1.0 or 1.1 load unchanged. Current contract constants: `ApiVersionMajor=1`, `ApiVersionMinor=2`.
- `StatisticsApi.TryGetHost(requiredMajor, minimumMinor, out IStatisticsHost?)` is a fail-closed negotiation check. A host 1.2 accepts minimum minor **0, 1, or 2**, rejects **3+**, and rejects every incompatible major. Callers that rely on `OwnerDisplayName`, `HasBreakdown`, or `RecordBreakdownEvent` must request `minimumMinor: 2`. No compatible SDK assembly loaded means the caller **must not invoke** `TryGetHost`; probe first.
- An incompatible future major must not replace the 1.x assembly with a breaking ABI under the same assembly identity. Introduce a side-by-side major assembly name or a carefully tested adapter bridge.
- This API is explicitly experimental: the final public compatibility policy will require in-game validation.

## Contract

`IStatisticsHost.Register(ApiMetricDefinition, Func<double?>? captureSnapshot = null)` registers at MOD construction, before the static acquisition scan. Late registrations return `Closed`. The host maps declarations to existing `ModMetricDescriptor`/P1 registry and save/profile renderer; no new store is created. Key format: `mod.<ownerPackageId>.<familyId>.<metricName>` (normalized lowercase). One family can contain multiple event metrics with the **same** owner, provider, revision and prerequisite set. A family is the opt-in and fault-isolation unit. Registering conflicting family metadata, invalid IDs, a mismatched snapshot callback, or a duplicate stable key fails closed.

A unit (`mod.<ownerPackageId>.<familyId>`) that a built-in integration of the host uses belongs to that integration, whether or not its MOD is loaded (#314). An SDK metric in such a unit is refused: `DuplicateMetric` when it repeats the built-in metric's key, else `ConflictingFamily`, even with the built-in provider ID, because the built-in family reads only its own metrics. The host logs one error naming the unit, records nothing for the refused metric (`RecordEvent` / `RecordBreakdownEvent` returns `Disabled`), and keeps the built-in statistic and the provider's other units working. To migrate, register under another `familyId` of the same owner (for example `mod.vanillaexpanded.vfesecurity.traprearm_sdk.extra` instead of `…traprearm.extra`). That is a new key: values recorded earlier under the refused key are not renamed or merged, and stay in the profile as they were. The built-in units are the ones `Source/RimworldStatistics/Metrics/IntegratedTransitionAdapters.cs` and the Vehicle Framework snapshot declare; in the game, the per-unit list under **Options → Mod Settings → Rimworld Statistics** shows every unit, with its ID in the tooltip. (Hospitality, Recruitment, Dubs Bad Hygiene, Vanilla Trading Expanded and Smart Apparel Upgrade are integrated through this SDK, so they follow the ordinary SDK rules above.)

Scalar event metrics (`ApiMetricKind.Event`, `HasBreakdown = false`) use `IStatisticsHost.RecordEvent(metricId, uniqueEventId, value=1)` **only when a real event succeeded on the game thread**. The host controls the tick; the provider cannot set it. The ID must be stable within the saved timeline and have at most 128 characters. It is SHA-256 hashed before entering the checkpoint. It must not contain personal information in the first place. Values must be finite with `|value| <= 1e12`: `Count` accepts only 1; `Sum` accumulates signed values in `[-1e12, 1e12]`; `Mean` stores a sum and sample count (use `Overall="Ratio"`). Invalid inputs (`InvalidEvent`) weaken only the affected metric to `Partial` without tainting sibling metrics in the same family. Duplicate IDs are ignored even after save/load; the bounded 4096-key tracker fails closed when full, marking only that metric partial. A repeated event after loading a saved branch is suppressed within that branch; distinct branches do not share future events.

Breakdown event metrics (v1.2+: `ApiMetricKind.Event`, `HasBreakdown = true`, supported on `ApiEventMode.Count` and `ApiEventMode.Sum` only; rejected on `SaveSnapshot` and `Mean`) use `IStatisticsHost.RecordBreakdownEvent(metricId, uniqueEventId, breakdownKey, value=1)` on the game thread, with finite non-negative values (`0 <= value <= 1e12`; `Count` accepts only `1`). Calling scalar `RecordEvent` on a `HasBreakdown = true` metric or `RecordBreakdownEvent` on a `HasBreakdown = false` metric fails closed with `InvalidEvent`. `breakdownKey` must be a non-empty, trimmed identifier of at most 96 characters (`ExternalSdkMetricPolicy.MaxBreakdownKeyLength = 96`) with no control characters and no personal/pawn names (for example a stable DefName or category slug). Each metric tracks both the overall scalar total and per-bucket totals, deduplicated through the same 4096-digest SHA-256 event tracker, and enforces a strict per-metric limit of **64 distinct breakdown buckets** (`ExternalSdkMetricPolicy.BreakdownBucketCap = 64`). Once 64 buckets exist, events on existing buckets continue to record until an unseen 65th bucket arrives; the 65th distinct bucket fails closed with `CapExceeded`, marks the accumulator overflowed, and weakens the metric and its buckets to `Partial`, after which subsequent breakdown events on that metric (including existing buckets) also fail closed with `CapExceeded` (cross-colony aggregation treats absent buckets on a `Partial` colony as `Unknown`, never fabricating `0`).

Save snapshots (`ApiMetricKind.SaveSnapshot`) use an O(1) or bounded detached `Func<double?>`, called only after a successful game save, returning `null` for unavailable or a finite value within `[-1e12, 1e12]` (**never pretend unknown is 0**). Throwing or out-of-range data disables only that acquisition unit for the session. Do not capture or retain game objects, guest names, pawn IDs or per-person histories.

For both modes, choose `Category`, `Unit`, `Overall`, `Selection` from the existing P1 enums using exact case-sensitive member names (numeric strings are rejected). `Unit="Ranking"` and `Selection="ObservationMaxByBreakdown"` are reserved/prohibited in external registrations. Set `MinimumOwnerVersion`/`MaximumOwnerVersionExclusive` and optionally `RequiredPackages` if source-level API compatibility has been audited; unknown versions fail closed. `RequiredDlc` is a package ID. Only numerical aggregates and minimal owner/provider-version metadata are stored.

## Recording, opt-in and historical data

External SDK units are always **Unverified** (shown as experimental), but they are recorded by default like every other unit: a new installation of Rimworld Statistics selects all units, including units registered later, through the saved "all units" choice (`RimworldStatisticsSettings.experimentalUnitIds = ["*"]`, `experimentalEnabled = true`). In **Options → Mod Settings → Rimworld Statistics**, "Record all available statistics (on by default)" and the per-unit list (`mod.<ownerPackageId>.<familyId>` units appear under their MOD's name, with the ID in the tooltip) turn acquisition on or off. A change applies **at once**, in the running game, without a restart (`RimworldStatisticsMod.ApplyLiveSelectionIfChanged`); unticking one unit after "all" keeps the other current units and stops including future ones, and an empty selection is a deliberate opt-out. Registration itself does not record anything: hooks are installed once at startup when the owner MOD (and any required DLC) is loaded and compatible, and the selection decides, live, whether they record. Adding or removing a MOD still needs the restart RimWorld always needs. A unit that fails (an exception or out-of-range snapshot) stays off for the rest of the session and is retried after a restart.

Installed family descriptors are persisted to the existing profile upon a successful observation; future removal retains earlier observations. Saved event-family data is preserved verbatim when its MOD is absent. Reinstalling resumes same-revision data where continuous; missing intervals or definition revisions are treated as partial/new, not silently stitched. Checkpoint parent identity provides branch-aware counting. Recorded statistics are always shown, whether or not their unit is selected now or their MOD is loaded (the old `showRecordedExperimental` setting is kept in the settings file for compatibility and no longer has an effect); the Details tab's status filter can narrow the list to experimental statistics.

## Provider name ("MOD: name")

The statistic's own title never carries the MOD name; the UI shows the provider beside it as "MOD: name" (#298, #303). The built-in integrations take that name from the catalog in `Source/RimworldStatistics.Core/Stats/ModProviderNames.cs`, whether or not the MOD is loaded, so a profile shows the same name after the MOD is removed and under another MOD set; `tools/check_mod_provider_names.py` (run by `tools/check_keys.sh`) fails when a built-in owner package has no name there or a name is not on `docs/supported-mods.md`.

In SDK 1.2, an external provider can optionally declare `ApiMetricDefinition.OwnerDisplayName` (trimmed, 1–128 characters, no control characters, and never equal to the raw `OwnerPackageId`), and the host also automatically captures the active MOD's loaded RimWorld title at startup into `ModMetricDescriptor.OwnerDisplayName` whenever active descriptors are saved to `profile.json` (backfilling existing same-provider, same-revision descriptors as well). After that external MOD is uninstalled, its recorded statistics keep showing the persisted MOD display name instead of reverting to `"External mod"`. Legacy v1.0/v1.1 profiles whose descriptors were saved before `OwnerDisplayName` existed continue to fall back to the generic `"External mod"` label until the MOD is loaded again; a raw package ID is never shown as a name.

## Example and CI

`examples/StatisticsSdkSample` in this repository is a separately built, development-only MOD (`pengin0503.rws.sdksample`) containing `SampleMod` and `SampleSdkClient`. It registers `mod.pengin0503.rws.sdksample.events.completed` (scalar event), `mod.pengin0503.rws.sdksample.events.by_kind` (v1.2+ breakdown event when negotiated against minor ≥ 2), and `mod.pengin0503.rws.sdksample.state.count` (save snapshot); a real integration calls `SampleSdkClient.OnConfirmedEvent(stableId)` / `SampleSdkClient.OnConfirmedBreakdownEvent(stableId, breakdownKey)` after a successful operation and `SetCurrentCount` with an observed aggregate. By default it requires API minor 0; build with `-p:RequiredApiMinor=1` or `-p:RequiredApiMinor=2` to require minor 1 or 2. Core tests verify P1 descriptor compatibility, checkpoint save/load forks, breakdown bucket-cap fail-closed behavior, persisted `OwnerDisplayName` survival after MOD removal, owner version fail-closed, invalid values, and bounded fast-path allocations.

From a clean checkout (with the .NET SDK; `-p:UseNuGetRefs=true` takes the game reference assemblies from NuGet, as CI does):

```bash
dotnet test Tests/RimworldStatistics.Core.Tests/RimworldStatistics.Core.Tests.csproj -c Release -p:UseNuGetRefs=true
dotnet build examples/StatisticsSdkSample/StatisticsSdkSample.csproj -c Release -p:UseNuGetRefs=true
dotnet build examples/StatisticsSdkSample/StatisticsSdkSample.csproj -c Release -p:UseNuGetRefs=true -p:RequiredApiMinor=2
UseNuGetRefs=true bash tools/package.sh host.zip   # as CI; or with .refs/ or GameDir/HarmonyDll instead of NuGet
python3 tools/check_sdk_package.py host.zip
```

The sample build writes `.devoutputs/sample/StatisticsSdkSample.dll` and copies no API, Core or host DLL. There is no packaging script for the sample: to try it in the game, make a MOD folder with `examples/StatisticsSdkSample/About/About.xml` as `About/About.xml` and the built DLL as `1.7/Assemblies/StatisticsSdkSample.dll`, and load it after Rimworld Statistics. `tools/check_sdk_package.py` checks that the host ZIP holds exactly `RimworldStatistics.Api.dll`, `RimworldStatistics.Core.dll` and `RimworldStatistics.dll` and no optional addon.

### In-game development buttons and fault isolation

When the independent sample MOD is enabled, open **Options → Mod Settings → Statistics SDK Sample (Development)** while playing a colony. **Simulate one confirmed sample action** increments its own save-persisted, branch-local ordinal and attempts to record one SDK event (and breakdown event when minor ≥ 2 is negotiated). The sample snapshots the current ordinal at successful saves; a disabled/missing SDK never stops the sample MOD. The sample does not poll every tick.

**Arm snapshot exception for the next save** intentionally throws exactly once from the SDK snapshot callback. The host must quarantine only `mod.pengin0503.rws.sdksample.state`, leaving the event family and unrelated units functional. This is a development test, never distributed with the production Statistics ZIP.

For step-by-step positive/negative game acceptance and performance measurement protocol, see `docs/sdk/p3-game-acceptance.md`.
