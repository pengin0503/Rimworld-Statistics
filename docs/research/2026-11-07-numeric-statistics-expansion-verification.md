## Phase A の確認結果

### 自動テスト

`dotnet test Tests/RimworldStatistics.Core.Tests/RimworldStatistics.Core.Tests.csproj -c Release -p:UseNuGetRefs=true` は 285 件すべて成功（`RWSTATS_REAL_SAVES_DIR` 指定時）。既存 174 件のうち、スキーマ番号を「新しい版」として使っていた 3 件だけを 2→3（および保存時の番号 1→2）に変更し、検査している挙動は変えていない。新規テストは `Numeric*Tests.cs` の独立ファイル。計画の数値例（`Wealth_Total=[100,150,120]`、`ColonistMood=[60,0,40,85]`／`[0,40,85]`、固定窓 30/31・120/121、クエストの成功 1/失敗 1/失効/途中/無効/同一 ID コピー、A の 1/2 と B の 9/10 で 10/12、除外・欠損・手動統合・同名別コロニー・逆順取り込み、最速エンディング 600000 対痕跡 300000 で 10 日）はすべてテストに固定した。主要な判定は変異テスト（条件を壊して失敗することの確認）で検出できることを確かめた。

### 実セーブ 49 件

- v1 の合計（33 コロニー、通算 135,723,149 tick、襲撃 190、死亡 29、最高資産合計 4,364,583 等）は変化なし。未変更の再走査は 0 件読み込み。全ファイルの SHA-256 は取り込み前後で一致。
- 7 系列（`Wealth_Total/Items/Buildings/Pawns`、`FreeColonists`、`Prisoners`、`ColonistMood`）はすべてのセーブで 1 回ずつ現れ、点数は `floor(ticksGame/30000)+1` と一致、非有限値なし。**取得根拠の「1.5/1.6 は匿名実セーブで間隔を裏づけるまで時間を使う出力を無効」の条件は、この 42 件（1.5 系 22・1.6 系 20）で満たされたものとして、1.5/1.6/1.7 で時間付き出力を有効にした。** その他の版は時間付き出力なし（系列ごとの開始整合の判定は従来どおり各セーブで行う）。
- statsRecord の省略時既定値: 1.7 は `StatsRecord.ExposeData`（1.7.4985）で `numRaidsEnemy`・`colonistsKilled` が既定 0。1.5/1.6 は 42 件で、明示された `numRaidsEnemy`・`colonistsKilled` が一度も 0 ではなく、`greatestPopulation` が一度も 3 ではない（Scribe が既定値を省略することと整合）。これを根拠に 1.5/1.6 でも省略を 0 とした。
- 数値観測は全 33 コロニーに帰属し、帰属不明 0。同一コロニーで後のセーブに置き換わった観測を除くと 41 件。数値ビューの作成は約 4 ms（初回 36 ms）。

### 性能（受け入れ計測 1）— 目標の境界上、この環境では安定して満たせていない

空のプロファイルへ 49 件を初回取り込み（別プロセス、v1 と交互に 5〜9 回、中央値）。同じ 4 vCPU の VM でも v1 自体が回ごとに 3.2〜3.7 秒と揺れ、比は計測のまとまりごとに次のとおりだった。

| 計測 | v1 | 本版 | 比 |
|---|---|---|---|
| 取り込み全体（1 回目のまとまり） | 3.71 秒 | 4.38 秒 | 1.18 倍 |
| 取り込み全体（2 回目） | 3.28 秒 | 4.13 秒 | 1.26 倍 |
| 取り込み全体（最終コード） | 3.24 秒 | 4.22 秒 | 1.30 倍 |
| 読み取りのみ（プロファイル書き込みなし） | 2.93 秒 | 3.56 秒 | 1.22 倍 |
| 同じプロセスでの 2 回目以降（温まった状態） | 2.23 秒 | 2.49 秒 | 1.12 倍 |

**目標（3 回の中央値で 1.25 倍以下）は境界上で、この環境では満たせない回がある。** 原因の切り分け（変種を作って交互に計測、CPU サンプリング）: SHA-256 の計算自体は 2 本目のスレッドで重なり、外しても時間は変わらない。数値観測の作成は 49 件で約 40 ms、GC は 2 回・約 10 ms。主な差は、XML の読み取り経路にハッシュ用のストリームを挟んだことによる主スレッドのバイトコピーと受け渡しの同期（読み取りのみで約 0.6 秒）と、大きくなったプロファイル（約 300 kB、v1 は 66 kB）の取り込み中の書き込み。XmlReader の内部バッファー、受け渡しブロックの大きさ（64 KB〜1 MB）、ジェネリックの JIT を変えた変種では改善しなかった。仕様の「解析したバイト列を同じ読み取りで同時にハッシュする」を保ったまま、これ以上の削減は見つけられていない。判定は計画どおり利用者の PC（同じ版・データ・ハード）で行う（[手動確認の手順書](../manual-test-checklist.md) §2）。

### 実装で確定した解釈

- 観測窓が作れない系列（点数が窓より少ない、開始値 > 0 の区間がない等）、成功クエストがない場合の所要日数は「対象外」とし、全体の母数から外す。0 ÷ 0 の率は「既知の 0 件」として合算に入れ、コロニー別は「—」。欠測による不明だけが全体値を部分記録にする（取得根拠の「対象窓なしは—」と設計 §2 の NotApplicable を合わせた扱い）。
- 同じコロニー同定（指紋・キャンペーン ID・開始入植者集合が一致）で、より後の tick の観測があり、観測横断の値（MOD 数）も同じ古い観測は、表示値を一切変えないため保存しない（設計 §2「等価と証明できる場合だけ枝刈り可」）。オートセーブが変わるたびに観測が増え続けることを防ぐ。
- クエスト ID 0 は有効な ID（`UniqueIDsManager.nextQuestID` は 0 から、Scribe の既定も 0）。

## 未実装の Phase と残る確認

> 追記（Phase C 実装後）: C0〜C4 は取得コードと Harmony パッチを実装し、取得単位ごとのゲート（既定で閉）と未公開のカタログ登録まで済ませた。下の C の表は実機で残る確認としてそのまま有効。状態・設計・調査結果・保留の根拠は [Phase C の実装記録](2026-11-07-numeric-statistics-phase-c-implementation-notes.md) を参照。

## 記録ファイルの移行と戻し方

- 初めて本版が記録ファイルを書き換えるとき、読み込んだスキーマ 1 のファイルを `profile.v1.json` として 1 回だけ保存する（既にあれば上書きしない）。この保存に失敗したら新スキーマは書かない。
- v1 の MOD はスキーマ 2 の `profile.json` を読取専用で開き、上書きしない（v1 のコードで確認済み）。
- v1 へ戻すとき: ゲームを終了し、`profile.json` を別名で退避してから `profile.v1.json` を `profile.json` にコピーする。本版へ戻すときは退避したファイルを戻す。両版で別々に記録した内容は自動では統合しない。
