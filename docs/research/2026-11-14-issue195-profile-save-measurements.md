# Issue #195：プロフィール保存の再評価・実測・改善（2026-11-14）

対象：[Issue #195](https://github.com/pengin0503/Rimworld-Statistics/issues/195)、基準 main `1841490`（PR #258 マージ後）
計測環境：このセッションのLinuxコンテナ（.NET 10.0.404、Release、共有CPUで揺れが大きい）。**実ゲーム・Windowsでの計測ではない**。

## 2. 代表的な形のプロフィール

既存の `--large` は保存観測の水増しが中心だった。6件の実セーブを読み取り専用で取り込んだプロフィール（169KB）の内訳は、チェックポイント末端が約51KB、セーブファイル観測が約8.8KB。これに合わせ、コロニーごとに「全SaveFile統計を持つ8セーブ」「全ライブ統計＋内訳を持つ末端チェックポイントと圧縮済み祖先」を作る合成データ（`ProfileBenchmark --representative`）を追加した。実データは使っていない。

## 4. 実施した改善

1. **UTF-8バイト列で直列化・比較・書込**（`ProfileJson.SerializeToUtf8Bytes`、`ProfileStore`）：出力はUTF-16経由と1バイト単位で同一（テストで確認）。読み戻しはデコードせずバイト比較、書込は再エンコードなし。
2. **他セッション検出をバイト完全一致に**：従来のデコード後の文字列比較では、デコード結果が同じになる編集（不正なUTF-8バイトの置換など）を見逃していた（テストで旧実装の失敗を確認）。読込時にBOM付きだったファイルは、読込時の生バイトを期待値にするので誤検出しない。
3. **ゲームスレッドが待たない記録**（`ProfileSession.MutateWithoutBlocking`）：プロフィールが空いていればその場で適用。別スレッドが保持中なら順番付きのキューへ入れて即座に戻り、ワーカーが解放直後に適用する。**以後の読み書き・保存・終了処理はすべて先にキューを適用する**ので、後の変更だけが見える・ファイルに入る状態は起きない。`RecordSave` だけがこれを使い、失敗はゲームスレッドで記録する。
4. `profile.v1.json` は読み込んだ旧形式ファイルを**バイト単位でそのまま**保存（従来はデコード後の再エンコード）。

## 5. 実施しなかったもの（理由）

- **更新日時・サイズだけの競合判定**：安全性が下がるため不採用（全バイト比較を維持）。
- **ロック外での直列化**：不変スナップショットがないと、書込途中の状態を保存しうる。ゲームスレッドの待ちは3.で解消したため、危険な変更はしない。
- **統計変更時のバックアップ判定の2回解析**（10MBで約101ms）：バックグラウンド書込スレッドの処理で、ゲームスレッドは待たない。プロパティ順の違いを同値とみなす現在の判定を正確に保ったまま省略する方法は複雑になるため、今回は変更しない。
- 追記型・差分保存などの形式変更：既存プロフィール形式と互換性を壊すため不採用。

## 6. 安全性の確認（テスト）

既存：別セッションによる上書き拒否（同サイズ・同時刻の編集を含む）、取込状態だけの変更でバックアップを回さない、3世代バックアップ、破損プロフィールの退避と復旧、旧schemaの原本保護、新しいschemaの読み取り専用、取込キャンセル。
追加：BOM付き一次ファイル、デコード結果が同じ編集の検出、UTF-8出力の同一性、キュー適用の順序・待たないこと・ファイル反映・終了時反映・失敗の隔離・変更中の再入、連続バックグラウンド書込中の300回の変更がすべて残ること（20回反復で不安定なし）。
