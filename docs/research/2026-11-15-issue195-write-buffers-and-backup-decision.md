# Issue #195：書込バッファの再利用と、解析しないバックアップ判定（2026-11-15）

対象：[Issue #195](https://github.com/pengin0503/Rimworld-Statistics/issues/195)、基準 main `c12f7ad`（[前回の計測](2026-11-14-issue195-profile-save-measurements.md)・PR #259 の後）
計測環境：このセッションのLinuxコンテナ（4 vCPU 共有、.NET 10.0.404、Release、ワークステーションGC）。揺れが大きい。**実ゲーム・Windowsでの計測ではない**。

## 1. 着手前の内訳（main、10MBの代表的プロフィール）

前回の残課題を、書込1回の段階ごとに測り直した（`--representative` と同じ合成データ、中央値）。

| 段階 | 5MB | 10MB |
|---|---:|---:|
| ロック内の直列化 | 19.1ms（割当 19.2MB） | 38.8ms（割当 37.8MB） |
| 一次ファイルの読み戻し照合 | 1.0ms | 2.3ms |
| **統計が変わったときのバックアップ判定**（`JsonDocument` 2回＋`DeepEquals`） | **36.8ms** | **49.0ms** |
| 取込状態だけ変わったときの判定（前後一致の比較） | 0.9ms | 1.7ms |
| 書込＋fsync / 置換 / 回転 | 8.5 / 3.5 / 3.4ms | 16.5 / 5.3 / 5.6ms |

統計が変わる書込（セーブ記録・取込の大半）では、バックアップ判定の解析が最大の項目だった。直列化の割当37.8MBの大半は、書込のたびに作る**プロフィール全体の配列**（85KB超でLOH、gen2回収の原因）と、観測1件ごとの `SerializeToUtf8Bytes` の配列だった。

## 2. 実施した改善

1. **統計の差を解析せずに証明する**（`ProfileStore.CanonicalStatisticsDiffer`）
   既存の判定（importState以外が構造的に同じか）は、オブジェクトのプロパティ順の違いと数値の表記（`0` と `-0`、`1` と `1.0`）を同値とみなす。前回はこれを正確に保つ方法が複雑として見送った。
   今回は、前回もこのストアが直列化器で書いた出力どうしに限り、次を使う：直列化器は同じ値を常に同じバイトで書き、二通りに書きうる数値はゼロ（`0`/`-0`）だけ、ファイルから保持したJSON（未知フィールド・隔離した観測）は読んだまま書き戻す。したがって importState 以外が同値なら、共通の先頭・末尾を除いた区間で **`-` 以外の各バイト値の出現数が一致する**。一致しないバイト値があれば確実に差があり、解析を省いてバックアップを回す。一致した場合（配列要素の入替など）・直列化器の出力でない場合（読込直後のファイル、`SaveSerialized`）・レイアウトが違う場合は、**従来どおり両方を解析して比較する**。誤判定は「差があるのに回さない」方向には起きない。
2. **書込バッファの再利用**（`ProfileBuffer`、`ProfileStore.SaveCanonical`）：プロフィールは、書込の間で保持する2つのバッファのどちらかへ直列化する。片方は最後に書いた内容（別セッション検出の期待値）を持ち、もう片方へ次を書く。書込のたびのプロフィール全体の配列（LOH）がなくなる。常駐メモリは、期待値1つ分から、2つ分（＋伸長の余裕1/8）に増える（10MBで約12MB増）。
3. **観測1件ごとの配列をなくす**（`MetricObservationsConverter`）：スレッドごとに再利用する作業バッファへ書く（1MBを超えたら保持しない）。出力は従来と1バイト単位で同一（テストで確認）。

ファイル形式・バックアップの世代・別セッション検出（全バイト照合）・アトミック置換・保存要求の合流は変えていない。

### 変わらないもの

- 読込量・書込量：書込ごとに一次ファイル全体を読んで照合し、全体を書く（10MBで各10.55MB）。照合を日時・サイズで省略することはしない。
- バックアップ回転：統計が変わった12回はすべて回転、取込状態だけの12回は回転なし（両ビルドで同じ）。
- `RecordSave`（`MutateWithoutBlocking`）の待ち：p95 0.02〜0.03ms（両ビルド）。

### GC

- 計測の12回ではどちらもgen2は0回。直列化だけを60回連続した別計測（10MB）では、main がgen2を9回、本PRは0回（LOHの配列がなくなったため）。
- 直前にフルGCを行ってから60回直列化した計測では、GC停止の合計はどちらも約2〜3ms（gen0：main 6回×0.3〜0.4ms、本PR 3回、うち初回のみ1.5〜2.6ms）。停止時間の悪化はない。
- 改善2と3の内訳（10MB、直列化のみ、再利用バッファ上）：改善2で 35→27.5ms・割当 37.8→27.1MB、改善3で 27.5→25.9ms・割当 27.1→17.4MB。改善3の時間への効果は小さい（約6%）が、割当とgen0回数は明確に減る。

### 背景書込が途切れない状況での `Mutate`（ブロッキング）の待ち

`--representative` の `blocking_wait` は、背景書込を休みなく続けさせた人工的な状況での値。10MBで20秒ずつ交互に3回測ると（中央値 / p95 / p99 / 最大）：

| | 中央値 | p95 | p99 | 最大 |
|---|---:|---:|---:|---:|
| main | 0.0ms | 27.8〜34.7 | 45.2〜48.0 | 97〜139 |
| 本PR | 9.5〜24.9ms | 28.9〜32.1 | 36.9〜43.6 | 123〜130 |

書込のうちロック外の部分（判定など）が速くなり、休みなく書く状況ではロックを持つ時間の割合が上がる（約36%→約58%）ため、中央値は上がる。p95以上は同等以下。実際の背景書込は取込中5秒ごと・セーブ記録時・除外操作時で、連続しない。ゲームスレッドのセーブ記録は待たない経路（上表）を使う。

## 4. 実施しなかったもの（理由）

- **ロック外での直列化**：不変のスナップショットが必要。JSON往復による複製（10MBで126ms）は直列化（39ms）より遅く、効果がない。
- **更新日時・サイズによる照合の省略**：同サイズ・同時刻の書換えを見逃すため不採用（全バイト照合を維持）。
- **`MetricEntry` の手書き直列化**：残る割当（10MBで約16.5MB、直列化器内部の作業領域）はgen0で短命。手書きにすると既存の互換性（未知フィールド・表記）の保証を作り直すことになり、危険に見合わない。
- **取込完了時の書込の省略**：`lastScanUtc` は取込タブの表示に使う（仕様 §6.3）。
- 追記型・差分保存などの形式変更：既存プロフィールとの互換性を壊すため不採用。

## 5. 安全性の確認（テスト）

追加（`ProfileWriteCostTests`）：
- 再利用バッファの出力が `SerializeToUtf8Bytes` と1バイト単位で同一（Unicode名・`-0`・NaN・隔離した観測・未知フィールドを含む）。観測ごとの書出しも従来と同一。
- バックアップ判定が構造比較（オラクル）と全ケースで一致：取込状態だけ、同じ長さの値変化、値の入替、桁の並べ替え、辞書の順序だけ、ゼロの符号だけ、観測の追加・削除、同じ長さの文字列変化など。解析を省く経路と従来の経路の両方を通ることを確認。
- 直列化器の出力でないJSON（数値表記 `0.10` など）と、その後の通常書込で誤って回転しない。
- 外部の書換え（同サイズ）の検出、書込失敗後の再試行、2つのバッファの交代が期待値を壊さないこと。
- 大きな観測400件の書込で、割当がプロフィールの1/4未満（main ではこのテストだけ失敗）。

保護を1つずつ外す変異テストで、各保護が上記のいずれかで検出されることを確認した。既存の保存・バックアップ・復旧・同時実行のテストはすべて成功。
