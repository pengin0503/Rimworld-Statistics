# Post-v1.4 private five-save evidence audit — 2026-11-10

Scope: **research only**. Baseline `main@f6890ee626bceb087693136a304333ce089d926c` (v1.4.0). Five *new* private RimWorld 1.7 .rws originals, **not** the earlier five-save chain documented by PR #79/#80. No source-code, profile-schema, acquisition-gate, release, or existing Issue changes.

## Evidence levels and privacy

- **[S] Original-save observation:** independent, read-only Python/lxml XML parsing and in-memory JSON/checkpoint comparisons on all five attachments. Before/after byte SHA-256, byte length and file mtime were identical for all 5. The hash values themselves are **not published**. This is **not** production `SaveReader`/.NET or in-game acceptance.
- **[C] Code/repository inspection:** current `main` source and open Issues viewed via the authenticated GitHub connection.
- **[I] Conditional proposal:** implementation feasibility, not established correct runtime behavior.
- **[U] Unresolved:** needs a controlled game scenario, a historical Def database, private profile, or other independent saves.

No original filenames, exact checkpoint/campaign/pawn identifiers, world names/seeds/tiles, complete MOD lists, full XML/JSON, contents or hashes, local paths, or personally identifying details were uploaded. All five are aliases **A–E** ordered by *in-game tick*, never five independent colonies.

## 2. Five-file observations and ancestry [S]

All five parse as well-formed XML; contain **one valid JSON formatVersion=1 `numericStatistics` checkpoint** each; report game version `1.7.5000 rev1275`, the **same exact ordered 192-entry MOD inventory**, the same campaign identifier and world/starting-colony fingerprint inputs, and matching saved `ticksGame == checkpoint.saveTick`. The five checkpoint IDs are distinct. Of the five canonical DLC packages, four are present and one absent (do not infer an individual family's applicability from whether its counters are empty).

| Alias | Game-tick displacement from A | Embedded checkpoint entries | Parent among these five | Vanilla enemy-raid/death counter change from previous row |
|---|---:|---:|---|---|
| A | 0 | 22 families / 101 family metric states | Not among supplied five | N/A |
| B | +62,500 | 22 / 101 | Not among supplied five | 0 / 0 |
| C | +125,000 | 22 / 101 | **B (exact parent checkpoint ID)** | 0 / 0 |
| D | +187,500 | 22 / 102 | Not among supplied five | 0 / 0 |
| E | +274,203 | 22 / 104 | Not among supplied five | +1 / 0 (**not proven interval**) |

**Only B→C is a proven direct parent edge** among these five, with +62,500 ticks and **zero** vanilla raid/death counter deltas. A→B, C→D and D→E are *not* proven direct edges; missing intermediates or different branches cannot be distinguished by these files. A common identity plus strictly increasing ticks **does not prove linear ancestry**. The raid counter increase across unproven D→E **cannot** be promoted into a verified event interval or a precise dated event. A conditional direct-edge interval always remains `Partial`, non-additive to existing lifetime counters, per `HistoricalCounterIntervals.Evaluate`.

All **22 checkpoint families** per file have `evidence=experimental` and `continuous=true` over their respective captured intervals. Twenty families have one common **non-zero** start tick; two newer families have another, later **non-zero** start tick. This excludes any assumption of full-campaign coverage. Three present families have an empty metrics dictionary in all files; **empty is not measured zero and is not by itself DLC N/A**. The five are **one colony**, therefore must contribute at most one representative colony to cross-colony totals/rankings (not five). Any genuine independent-colony leaderboard requires an additional fixture.

Each original has one saved map; its `things` list contains roughly **11.8k–12.5k serialized map Things**, with **89–103 elements tagged Pawn**; these are not necessarily all free colonists. `researchManager/progress` contains **123 matched keys and values per save**, with **75–78 positive values**. Positive research progress cannot, without matching historical `ResearchProjectDef` cost/finish/techprint rules, be treated as a completed project. These measurements are sanitized *shape counts*, not player-facing statistics.

## 3. Existing by-type counters: five-save consistency [S,C]

Each of the five original checkpoints independently satisfies these invariants:

| Saved fields (checkpoint family/state) | Supported evidence | Count of distinct type keys observed |
|---|---|---:|
| `work.sown.n == Σ(work.sown.by)` | 5/5 exact (sown *events*, not crop yield) | 8 |
| `trade.sold_units.n == Σ(trade.sold.by)` | 5/5 exact *item quantity*, not sale silver | 19–22 |
| `trade.bought_units.n == Σ(trade.bought.by)` | 5/5 exact *item quantity*, not spend | 11–12 |
| `work_details.crafted.n == Σ(work_details.crafted.by)` | 5/5 exact for recorded interval | 18–23 |
| `work_details.mined.n == Σ(work_details.mined.by)` | 5/5 exact for recorded interval | 1–2 |

The `work_details`/ `chore` families started later than the other 20, hence their counts are **Partial relative to full play history**, even though internal splits balance exactly. **No decrease was found for comparable saved scalar `n`/`sum` pairs along the sole proven B→C edge**, but event correctness and general monotonicity across unobserved branches remain unverified. The count of family metric state keys (101–104) must **never** be confused with 415 output definitions.

Existing `CrossColonyCatalog` supports top item/category only for a curated subset. **[I]** A complete sorted leaderboard with quantities and independently attributed colony contributions can be computed *from complete, compatible by-Def captured breakdowns* without new game hooks, subject to explicit definition/revision, unit, source-period, MOD Def identity, and 4,096-breakdown-key overflow checks. Aggregate each **independent colony's one valid representative** per Def, then sort; never sum every save of one colony, or sum each colony's individual top winner. When a by-Def sum does not reconcile to its authoritative scalar, mark result Partial and do not claim a complete ranking. This sample verifies algebra on one colony, **not** two-colony behavior.

## 4. Diagnosis of 0/35 and 1/35 [C,S,U]

The 5 supplied saves represent **one identified colony** and do **not** contain the user's separate 35-colony profile or complete profile flags. It is therefore **impossible to attribute each displayed 0/35 or 1/35 to one cause** using this set alone. `NumericRow.Targets/Valid` counts selected applicable/known colonies, not raw saves.

| Cause | Can these files establish it? | Rule for an implementation |
|---|---|---|
| Acquisition disabled/not yet started | Non-zero `sinceTick` demonstrates incomplete life coverage for these checkpoints; not settings state for all 35 colonies | Missing/Unknown or Partial, never zero |
| Event did not happen during capture | Some family metrics are absent, but absence cannot distinguish no event from no hook | A *measured zero* requires positive acquisition evidence and semantics |
| XML reader/backfill not implemented | **Yes [C]**: reader skips most large maps/pawns/research state; #71 lists 38 outstanding snapshot outputs | Unknown until supported bounded validation |
| Runtime capture failure/hook mismatch | **Not proven [U]**; requires controlled successful event + save/reload and per-row expected values | Defect only after reproducible positive/negative test |
| Required DLC absent | One DLC missing in the supplied MOD inventory; exact per-metric `RequiredDlc` must be checked. Empty DLC-family values even with other DLC present do not imply N/A | `NotApplicable` **only** with proven absence for that metric |
| No valid lineage / older profile / MOD difference | Parent gaps exist; saved inventory is identical *within these five* | Missing link remains unknown; never add branch counters; preserve old-profile observations |

For the 35-colony coverage question, the next isolated test needs a **private, redacted profile-level diagnostic** of `Targets, Valid, Coverage, Evidence, Acquisition` per metric and per-colony availability (no names/IDs); **not** publication of the real profile.

## 5. Recovery feasibility [S,C,I]

| Area | Existing/observed input | Defensible output and boundary |
|---|---|---|
| Vanilla stats/wealth history | `storyWatcher/statsRecord`, `history/autoRecorderGroups`, retained quests | Existing supported saved-counter and recorder observations; exact **as saved**, not invented event dates or lifetime item gains |
| Faction relations and player home maps | Explicit world-faction relations, `worldObjects` and map parent references | **Already implemented** limited Partial signals; a recorded positive map count is a lower bound, **not** a proven historical maximum |
| Research | 123 keyed `researchManager/progress` entries in each save | Raw keyed progress is exact at saved tick; **completed-project count remains Unknown** unless historical Def/cost/DLC/techprint/finish semantics are validated |
| Population/medical state | Map and world serialized Pawns, ownership/guest/container/hediff fields | Bounded, deduplicated **saved-state partial snapshot** potentially recoverable; map Pawn element counts are **not** valid free-population totals; no historical joining/treatment/surgery events |
| Inventory | Serialized `things`, `stackCount`, holders, minified, equipment, caravans | Typed stock **saved-time** observation only after full ownership and ThingID-dedup rules; a filtered verified subset may be Partial; no inference of lifetime items bought/consumed |
| Facilities | Saved buildings/comp state and map parents | Medical beds, turrets, generators *at save* plausible after matching 1.7 Def/Comp semantics. Generator **on/off** cannot be inferred solely from a building Def. No peak without bounded supporting observations |
| Wealth | Existing recorder snapshots | Historical samples/peak within recorder scope; sum of each colony's representative saved wealth is **not** total wealth ever earned |
| DLC/MOD metrics | Saved ordered MOD inventory; game-specific components | `NotApplicable` when missing required DLC; unknown on mismatched Def/version, no reverse engineering of absent content |

No additional historical **event sequence** can be reconstructed reliably from these five snapshots. Experimental acquisition must remain opt-in.

## 6. Performance and compatibility [C,I,U]

- `SaveReader.ReadDetailed` streams XML with `XmlReader`, skips most maps and other irrelevant subtrees, computes a streaming content hash, checks before/after file metadata, and returns an error rather than replacing good data on failed reread. Keep these safeguards.
- `ImportEngine.Run` is serial by sorted save filename, checks `NeedsRead` per file, commits a checkpoint *before* its related SaveFile observation, persists periodically, and skips unchanged size+mtime+reader-version entries. `ProfileMutations.NeedsRead` currently uses a linear `Any` over existing saves per file: a **candidate** for a per-scan immutable lookup, only after representative and alias invariants are covered by tests.
- `CrossColonyAggregator.Build` already builds an index of **needed source keys only**; do not propose redundant full-catalog indexing. Large `things` lists mean any new recovery should read *bounded targeted XML paths only*, and never scan all Pawns/Things on every game tick.
- Current files have identical MOD/version inventories; **multi-MOD/DLC, old profiles, version mismatch, removed Def/provider and modified-save mid-scan are untested here**. Retain acquisition revision, `MetricCoverage.Unknown/Partial/NotApplicable`, provider descriptors, and last-good observation semantics.
- **No production .NET save import, real-game launch, TPS/save measurement, or 55+ real-save benchmark was executed in this audit.** Prior 5-original .NET figures in #71/#72 are from a **different** original set and must not be presented as measurements of these five. The previously reported synthetic 55-save tests are not a real-world baseline.
