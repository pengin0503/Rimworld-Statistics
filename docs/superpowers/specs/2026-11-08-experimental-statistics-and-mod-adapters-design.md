## 1. 目的と範囲

利用者が未検証の数値取得を**同じRimworld Statistics本体のMOD設定から明示的に有効化し、その統計を「実験的」と表示**できるようにする。あわせて、将来の他MOD独自のゲームイベント・建築物・資源・研究・職業等の統計を、一貫したコロニー照合・チェックポイント・集計・表示基盤に追加できる拡張設計を定める。

既存の「タイトル画面から全セーブ・全コロニーの通算値を数字で表示する」という目的を変更しない。既存A/D1の公開行、v1集計、セーブの成功判定・巻き戻し、v2プロファイルバックアップ、RimSaves併用可能性を維持する。

### 現状に基づく事実

- `AcquisitionUnits.All` は30単位: Family 20（通常Phase C 16 + DLC 4）、Snapshot 9（通常Phase B 6 + DLC 3）、Derived 1（`ending_party`）。30単位の`Status` はすべて `Unverified`。Derivedはフックではなく取得済み基礎値からの派生。
- `MetricGates.IsOpen` は `Verified` または Verify Harness による一時開放のみ通し、`MetricAdapters` は起動時の `[StaticConstructorOnStartup]` で必要なHarmonyクラスを適用する。
- `MetricRegistry.All` は検証済みの静的な表示リストで、`Catalog` には未公開の定義も存在。`MetricCalculator.BuildView(..., definitions)` は定義のリストを受け取れるが、`ProfileSession` のキャッシュ/描画側は表示フィルタの状態を考慮していない。
- `RimworldStatisticsSettings` は現状 `includeDevMode` と `autoImport` のみ。`Profile.metricObservations` およびCの `CheckpointPayload.Families` に数値が保存され、未知キーは保守的に保持する。
- 開発専用Verify Harnessは別MODかつ `-savedatafolder` 必須。一般ユーザーが使う有効化UIではない。

### 非目標

- 全30単位を根拠なしに `Verified` とすること。
- 他MODの生イベントログ、人物名・個人情報、長大な全時間系列を保存すること。
- 開発用Harnessを製品ZIPに同梱すること。
- すべての他MODを自動解析・自動統計化すること、任意の外部DLLをダウンロード実行すること。
- 統計表示をグラフ中心に変えること、既存の5タブを削除すること。
- この設計段階で製品コード・CI・PRのマージ・リリースを変更すること。

## 2. アプローチ比較と採用案

| 方式 | 利点 | 欠点 | 判断 |
|---|---|---|---|
| 全単位の `Status=Verified` 化 | コード変更が少ない | 未検証という証拠を偽装、通常利用者に無断でパッチ適用 | 不採用 |
| Verify Harnessを製品に同梱 | 現行の開放経路を再利用 | 起動引数と別MODが必須、UIなし、一般セーブへの汚染リスク | 不採用 |
| **検証状態と利用者選択を分離した実験取得ポリシー** | 既存の保存と取得基盤を維持、既定OFF、単位別停止可、正式検証後に昇格できる | 設定/表示/キャッシュ/保存履歴の追加設計が必要 | **採用案** |

他MOD統計についても、最初から外部SDKを公開する方式より**内部アダプター登録→実際の1 MODで実証→安定API公開**の順にする。先にAPIを固定するとRimWorldや対象MODの互換性変化に対応しにくい。

## 3. 実験的機能（製品内）の仕様

### 3.1 利用者が見る設定

MOD設定に独立した「実験的な統計取得」セクションを追加。日英の翻訳キーを固定し、以下を配置する。

- **実験的な統計取得を許可する**（既定OFF、明示同意を要する）。初回有効化時は、未検証・処理負荷・記録漏れ・重複計上・後から補完できないイベントを警告。テキストは短く、詳細ヘルプを用意。
- 単位のチェックリスト（名称・説明・取得形態・必要DLC・状態・注意/負荷カテゴリ）。選択は正規 `AcquisitionUnit.Id` 単位。**初期選択なし**。「すべて選択」「すべて解除」「カテゴリ単位選択」を明示操作で提供。MODの更新で追加された新単位は自動ONにしない。
- `ending_party` はDerivedなのでフックのON/OFF項目に含めない。依存元（v1終了記録）の条件が満たされると表示対象になる。表示に要るデータが無ければ「—/不明」。
- DLCを持たない/無効の単位は「利用不可（DLC未導入）」と表示して選択・将来の設定値は保全。DLCが後から有効になる場合も**新規導入DLC単位の自動有効化はしない**。
- 「記録済みの実験統計を閲覧する」表示専用トグルを別途用意。収集停止時も既存記録は削除しない。表示OFFは単に画面から隠す。
- **Harmonyの適用範囲を変える設定は再起動後に反映**。GUIには「次回起動から反映」を表示し、実際に有効なセッション用設定スナップショットと未適用の希望値を区別。再起動なしの動的Unpatch/Repatchは行わない。
- 一度閉じた取得単位をセッション途中の設定操作だけで再開しない。確認済みの `Verified` 単位は実験トグルとは無関係に従来通り利用可能とする。

例（文字ベース、確定UIデザインではない）:

```text
[ ] 実験的な統計取得を許可する                 (既定OFF)
    未検証の統計です。記録漏れや負荷が生じる場合があります。
    [すべて選択] [すべて解除] [種類で絞り込み]
    [ ] 研究イベント (research)              イベント  Core
    [ ] 採掘・製作 (work)                    イベント  Core
    [ ] 保存時の施設情報 (facilities)        セーブ時  Core
    [ ] 汚染状態 (biotech_state)             セーブ時  Biotechが必要
[ ] 以前記録した実験統計も表示する
* 設定を有効にするにはゲームの再起動が必要です。
```

### 3.2 3つの状態を混同しない

- **Evidence status**: `AcquisitionStatus.Verified / Unverified`。検証根拠による開発上の状態。ユーザー設定で `Verified` にしない。
- **Recording policy**: `Verified` または「利用者が許可 + 単位を選択 + 前提MOD/DLCあり + 取得経路のパッチ成功 + 当セッションで失敗していない」なら記録可。既存Harnessの `OpenedForVerification` は独立した開発用経路のまま。
- **Visibility policy**: `Verified` の行は従来通り。未検証行はユーザーの表示選択に従って閲覧可能（実際の記録がない場合は不明）。同じ状態でも記録可否と閲覧可否を独立に判定。
- **Capture confidence**: 値がどの確証で取得されたか。完全・部分・保存時点・対象外という `MetricCoverage` とは**直交**する。「実験的/正式確認済み/混在/来歴不明」の概念を追加予定。既存Harness/旧データで根拠がない場合は遡って検証済みにしない。

### 3.3 フックの適用・失敗分離

- `MetricAdapters` は起動時に**実際の選択集合**を読む。`MetricGates.IsRecording` のDLC/エラー制約は維持。
- 同じHarmonyクラスが複数単位を提供するとき、パッチ自体は一度だけ。選択していない単位のカウンターは書かない。
- `Snapshot` 単位は従来通り「成功セーブ後」だけ読む。失敗保存・中断保存で確定しない。
- パッチ適用に失敗した場合は該当単位のみセッション終了まで停止し、ほかの単位や元ゲームの保存は失敗させない。1単位につき一度だけエラーログ。
- 異常な負荷が発生した際、ユーザーは次回起動から当該単位だけ無効化できる。ゲームスレッドでファイル入出力や全セル走査を増やさない。

### 3.4 データの正しさ・移行

- オプトイン前のプレイ期間のイベントは**復元不能なものがある**。`0` と表示せず `Partial` / `Unknown`、`sinceTick/throughTick` を保持。
- ON→OFF→ON、既存セーブの分岐、同tick別セーブ、プロファイル復元、別DLC構成、別MODロード順で「空白期間を完全値に足さない」。`LiveMetricAccumulator.Resume` の保存済みファミリー保持と中断判定を使う。
- 取得時点の実験的来歴を保存時に安定キーで残す。Cならファミリーの履歴属性、Bなら取得単位別のスナップショット属性、表示行なら最も保守的な属性へ伝播する。旧データで属性がない場合は `UnknownLegacy`。あとで `Verified` になっても古い値を自動で「実証済み」に書き換えない。
- `MetricCoverage` と取得時の確証を混同しない。集計で実験/正式の複数観測を合算する場合は `Mixed` を表示（割合等は同じ分母・範囲のみ）。不一致なら不明/部分。
- `Profile.CurrentSchemaVersion=2` と C `CheckpointPayload.CurrentFormatVersion=1` は可能な限り維持。追加フィールドはオプショナル・未知フィールド往復の契約を守る。非互換変更が必要だと判明した場合にのみ版上げ、保護コピー、移行を別途設計してCIで検証。
- 既存プロファイルの読み取りだけで自動移行しない。全ての前回実装のSaveSnapshot圧縮/観測件数/欠測/未来JSON保護を維持。

### 3.5 UI / 統計カタログ

- `MetricRegistry.Catalog` に登録された既存定義を再利用。静的な `MetricRegistry.All`（正式公開済み）を無断で未検証定義に置換せず、ランタイム用の `visibleDefinitions` を別の選択器で生成。
- `ProfileSession.GetView` のキャッシュキーに、表示対象の定義ID・実験表示設定を含める。既存のIncludeDevMode切替時と同様にキャッシュを更新。ランタイムGUIはimmutableなビューを描くのみ。
- 新しい行は「実験的」の表示を必須にし、カテゴリ・検索・並び替え・全コロニー/個別・内訳を既存の数値一覧と共通化する。グラフは追加しない。
- 説明欄には取得方法（イベント/成功セーブ）、記録開始時点、範囲/欠損、DLC/必須MOD、記録停止原因（任意の説明）を含める。
- 実験行の非表示、MOD削除、DLC無効化でも過去の観測を消去しない。未帰属のコロニーや除外設定も従来通り。

## 4. 将来の他MOD固有統計 — 拡張設計

### 4.1 スコープの分割

1. **内部共通基盤**: 他MOD用の取得単位・統計定義・保存・表示を登録できる仕組み。最初はRimworld Statisticsの本体内に同梱した、**任意MODが存在する場合だけ**使うアダプターを対象とする。
2. **実証アダプター1件**: 対象MODのバージョン、Package ID、Def・実ゲームAPIを先に監査してから1つ選び、セーブ時点の単純な値とイベント1種類の計測を行う。対象未導入のCIでもビルドできる。現時点で対象MOD・統計項目は確定しない（調査してから決める）。
3. **外部開発者向けSDK/API**: 互換アダプター1件の実証を経て実装方針を固定。第三者が別DLLで独自の指標を登録できるが、Rimworld Statisticsの内部クラスには依存させない。最初の一般公開時にAPI版番号を定める。

### 4.2 内部登録モデル（将来の型名案）

`IMetricProvider`（`ProviderId`, `RequiredPackageIds`, `Register(...)`）、`MetricProviderRegistry`、`ModMetricDescriptor`、`ModMetricAdapter` を責務別に分ける。API初期版では静的な宣言情報（id、必要MOD・DLC、定義リビジョン、出所、単位、演算、表示キー、任意の必要MOD版）を主に扱う。取得実行はゲーム側アダプターで行い、Coreの数値計算にはRimWorldの型を持ち込まない。

- 安定キー: `mod.<normalized-package-id>.<family>.<metric>`。IDはcase-insensitiveなPackage IDの正規化 + Ordinal安定なメトリック名。**ハッシュだけで識別しない**。既存の台帳キーと衝突不可。一度公開したキーの意味を変更する場合はrevisionを上げ、既存値を別の意味として加算しない。
- 必須MODが無い/版が不適合/必要Defが無い/アダプターが例外を出す場合は、該当providerまたは取得単位のみ記録停止。**欠落は0ではなくNotApplicable / Unknown**（過去に取得された正当な値は保持）。
- `providerId` と計測元MODのPackage ID・取得版を履歴へ残し、後からMODの追加/削除/バージョン変更があっても解釈可能にする。表示名や翻訳が無い場合は安定IDにフォールバック。
- 同じ出来事をバニラと対象MODの両方が通知した場合の重複計上を禁止。必要なら「元イベント優先」「MODの確定コールバック優先」等を指標ごとに決め、監査済みの事実だけを加算する。
- 既存 `MetricObservation` / `FamilyState` / `MetricCalculator` / `MetricRegistry` を共通化し、別プロファイル・別表示エンジンは作らない。キー削除時も過去データをQuarantine/保持し、一覧に「現在の提供元なし」を表示できるようにする。
- 追加MODが出す大量の品目/対象IDは4096件/ファミリー/キー軸の上限を踏襲。溢れた詳細は `Partial` に落とす。毎tickの総当たりは行わない。

### 4.3 対象MOD選定の条件（実装前の調査）

候補の選定は知名度だけでなく、**安定した取得箇所・統計の独自性・既存値との非重複・使用頻度・性能・DLC互換性**で評価する。対象MODの作者が提供する公開APIを優先し、なければ安定したゲームの確定イベント/Defを検討。APIの存在は実コード・対応バージョンで確認する。特定MODの動作やAPIの存在を今の時点で断定しない。

### 4.4 データ互換・ライフサイクル

| 変更 | 期待する挙動 |
|---|---|
| 他MOD未導入で起動 | Harmony適用なし、エラー・TPS劣化なし |
| 他MOD導入後に有効化 | 新たに記録開始、過去の不明期間は補完しない |
| 対象MODを無効/削除 | フック停止、既存記録・意味・revisionを保持、UIは提供元不在を明示 |
| 他MOD更新でAPI変更 | 対応可能な版のみアダプターを適用、失敗は該当単位だけ停止 |
| 他MOD再導入・セーブの枝分岐 | 以前の累計を二重加算せず、途切れた期間をPartialにする |
| 2つのproviderが同一キー登録 | 後から登録した方を拒否して診断、既存定義を上書きしない |
| 翻訳・Defが欠ける | 安定キー表示へフォールバック、全体のUIを落とさない |
| 本体が旧版/SDK新版 | 対応API範囲でのみ登録。未知JSONは保持して編集しない |

## 5. 段階、品質ゲート、受入条件

| 順 | 目的 | 実施単位 | 完了条件 |
|---|---|---|---|
| P0 | 製品内の実験的統計 | 設定・取得ゲート・公開一覧・来歴・試験・日英UI | 初期OFF、選択した取得単位だけパッチ、実験表示、セーブ分岐/再開/既存値保全 |
| P1 | 他MOD用の内部Provider設計 | 動的登録・名前空間・前提MOD判定・重複防止 | ダミーproviderによる起動/不在/衝突/復元の自動テスト |
| P2 | 実MODアダプター実証 | 対象調査を含む独立PR | 対象が無い環境で副作用0、通常の成功経路と二重計上を検証 |
| P3 | 必要なら外部SDK | API版・サンプル・互換試験 | APIに依存するサンプルMODが別アセンブリから動作し旧データを保持 |

- **受入テスト**: 新旧環境のCore単体テスト + 統合/静的Harmony参照チェック + 日英翻訳キー + 本体ZIPにVerifyHarness/ゲームDLLが混入しない検査 + 設定初期OFF/再起動前後 + 保存失敗/分岐/再取込/オフ期間/DLCなし + 既存v1回帰。
- **目標性能**（既存計画を継承）: Bの保存時追加コストは50ms以下、または旧版比5%以下の大きい方。C/Dの同条件60秒×5回のTPS低下中央値は2%以下が目標。追加作業メモリ64MiB以下。未測定の最適化効果を主張しない。予算超過した取得単位は実験モードのデフォルトOFFを維持し、警告する。
- **危険条件**: 資源の二重計上、既知値を0で上書き、元セーブ破損、同名別コロニー混同、通常OFF時にパッチ発火、未検証のVerified偽装、MOD不在時のロード例外、将来スキーマを破棄、成功していない保存を確定、パフォーマンス極端悪化。1つでも確認すれば該当タスク未完了。
- **レビュー分割**: P0/P1/P2/P3は独立PR・独立CI。P0のマージ・公開までP1〜P3のリリースを要求しない。外部SDKの本格実装は実証アダプター後に再レビュー。

## 6. 未確定事項と本案の暫定判断

- 実験的表示の初期状態は**既定OFF**。一括選択操作を用意し、個別停止可能にする。
- データ来歴はメトリックごとに保存することを推奨するが、現在のCheckpointのフィールド互換性と古いHarness観測の扱いはP0の最初にfixtureで厳密確認して最小限の追加フィールドに絞る。
- 最初に対応する他MODはP2開始時に実際の公開ソースとAPIを調査して決定する。対象を未調査で確約しない。
- 公開SDKはP2の使用例を経た後に策定する。APIの固定やSemVerの互換保証を今は行わない。
