# コロニー別統計履歴：セーブの親子関係に基づく線の接続（設計）

作成日：2026-11-14
関連：[Issue #72](https://github.com/pengin0503/Rimworld-Statistics/issues/72)、[次期開発候補調査 C1](../../research/2026-11-14-next-development-opportunity-audit.md)、[追加調査 §1](../../research/2026-11-14-additional-investigation-ja.md)、[グラフ設計（PR #255以前）](2026-11-14-metric-chart-drilldown-design.md)

## 1. 問題

PR #255 のコロニー別履歴グラフは、セーブ観測（`SaveFile`／`SaveSnapshot`／概要の基本値）を**同じ `ModCampaignId` なら前後の点を線で接続**していた。キャンペーンIDは「同じコロニー」の証拠であって、「同じセーブ分岐の連続した時点」の証拠ではない。巻き戻し・ロードし直し・兄弟分岐のセーブはすべて同じIDを持つため、ゲーム内日数順に並べると別の分岐の値を往復する線になり得る。

提供された6件の実セーブ（1.7.5005、読み取り専用）で現行mainを実行すると、親子関係の証拠がない 19:33→19:50 と、同じ古いチェックポイントを含むだけの 21:07→21:19 が線で接続されていた（設計上の誤りの実データ再現。ゲーム画面での目視確認ではない）。

## 2. 規則

線は「後の点のセーブが、前の点のセーブの子孫であることが証明できる」場合だけ引く。証明は埋め込みチェックポイントIDだけを使う（`CheckpointAncestry`）。

1. チェックポイントC自身のtickで保存されたセーブは、Cが記録した状態そのもの（**exact**）。
2. Cを含むがCより後のtickで保存されたセーブは、Cの**子孫**だが、C自身ではない。最後のチェックポイントを変更せず書き戻した保存である（`CheckpointSaveSession`／`LiveMetricAccumulator.PrepareSave`）。2026-11-15以降の版では、読めないチェックポイントの保持、入れ子の保存、保存フックが停止している場合にだけ起こる。それより前の版では、全ファミリーOFFの保存も該当した（§7）。このセーブを親として他の点を接続することはない。
3. チェックポイント同士は、一意・非衝突・同一キャンペーンで、子以前のtickを持つ親IDでだけ連鎖する。親欠落・衝突・循環・重複IDで連鎖は終わる。
4. 点Pは、Pの連鎖上で最も近い「exactな過去の点」に接続する。間に別分岐の点がある場合は `ContinuesFrom` で離れた点に接続し、隣の点（別分岐）とはつながない。
5. どの過去の点にも接続できない点は `Unlinked`（白抜き表示）。同じtickに別々のチェックポイントを持つセーブが混在する点（リロード後のオートセーブは同じtickに当たり得る）も、一つの状態とは見なさない。値が矛盾する場合は従来どおり欠測。
6. 欠測・Unknown・NotApplicable は値を持たない点のまま（ゼロにしない）。値のない点をまたいで線は引かない。
7. 同じtick・ファイル書込時刻・キャンペーンの組合せ、ファイル名、tick一致だけでは証明としない。ゲーム内のセーブ時スナップショットは、同じ保存で確定したチェックポイントIDを新たに `CheckpointKey` として記録し、以前の記録は取込済みセーブファイルの書込時刻とtickが完全一致する場合だけ対応付ける。

チェックポイント系統のグラフは従来どおり代表チェックポイントの親を辿る。追加で、同じチェックポイントがより後のtickのセーブにそのまま含まれていた場合、その最新のセーブtickを `SavedTick` として示す（「統計の取得時点」と「セーブ時点」の区別）。系統が親の欠落などで途切れた場合、それより前の記録も残す（§8）。

## 3. 実セーブでの結果（匿名化）

ゲームtick順に A〜F（19:33、19:50、19:54、19:56、21:07、21:19）。

| 点 | 接続 | 理由 |
|---|---|---|
| A | 始点 | — |
| B | 白抜き | Bの親チェックポイントは提供ファイルにない |
| C | B | 直接の親 |
| D | C | 直接の親 |
| E | D | EのセーブはチェックポイントE′（tick 12,348,927、親はD）を含む子孫 |
| F | D（Eではない） | FもE′を含むだけで、Eの子孫である証拠はない |

チェックポイント系統グラフ：B・C・D・E′の4点。E′は1点のみ（E・F両方に含まれる同一チェックポイントを二重計上しない）で、`SavedTick` はFのtick。

元ファイルのSHA-256・サイズ・更新時刻は実行前後で一致。再現は `RWS_PRIVATE_SIX_SAVES_DIR` を設定して `PrivateSixSaveChartLineageAcceptanceTests` を実行する（CIではスキップ）。

## 4. 表示

- 線：証明された親子関係のみ。白抜きの点：前の記録との関係が確認できないセーブ（凡例を表示）。
- ツールチップ：未確認の関係、離れた点からの分岐、「この記録は◯日のセーブにもそのまま含まれていた」。
- 大量の点の間引き（`MetricHistoryPlot.Thin`）はCoreへ移し、欠測・白抜き・分岐元の点を必ず残して参照番号を付け替える。描画のみで保存値は変えない。

## 5. 互換性と性能

- プロフィール形式：`MetricObservation.CheckpointKey`（null時は書き出さない）を追加しただけ。旧版で開いた場合は拡張データとして保持され消えない（旧版はその記録を圧縮対象から外すだけ）。スキーマ番号・累積値・既存の集計は不変。
- 合成プロフィール（10件ごとに巻き戻し分岐、Release、7回の中央値、同一ローカル環境で各2回）でのグラフ構築：100セーブ 約0.4〜0.6ms→0.7〜0.9ms、3,000セーブ 約11ms→21〜27ms。グラフを開いたときの1回だけの処理（プロフィールのロック内）で、ゲーム中の保存処理は変わらない。

## 6. 未検証

- 実際のRimWorld画面での描画・ツールチップの目視確認。
- 既存プロフィールに残る `CheckpointKey` 導入前のセーブ時スナップショットは、対応するセーブファイルを取り込んでいない場合は白抜きで表示される（誤った接続より安全側）。

## 7. 追補（2026-11-15）：実セーブ6件の調査を受けた修正

2026-11-15の調査で、6件は同じコロニーとして正しく判別されたが、次の3点が見つかった。

### 7.1 ツールチップ：「別の分岐」と「関係を証明できない」を区別する

`ContinuesFrom` の点（離れた過去の点から続く点）は、これまで常に「間にある点は別の分岐」と表示していた。F（21:19）は D（19:56）から続き、間の E（21:07）は同じ古いチェックポイントを運んでいるだけで、E が F の祖先かどうかは分からない。

`MetricHistoryPoint.SkipsOnlyOtherBranches` を追加した。間にあるすべての読み取り（同じtickでまとめた点は個々のセーブ）が自分のチェックポイントを持ち（exact）、そのどれもが後の点のチェックポイント連鎖に無い場合だけ true にする。exact な読み取りがその連鎖に無ければ、そのセーブは後の点の祖先ではない。後の点の連鎖は、離れた点まで途切れずに証明されているからである。チェックポイントの無いセーブ、古いチェックポイントを運んだだけのセーブ、または同じtickでまとめたセーブの一方が実は祖先である場合は false にする。表示は、true なら従来の `RWS_Chart_PointBranch`、false なら新しい `RWS_Chart_PointContinues`（「{0}日の記録から続いています。間にある点には、この記録との親子関係を確認できないものがあります（別の分岐とは限りません）」）にした。間引きで隣接になった点では false に戻す。

### 7.2 統計に変化がない保存でも新しいチェックポイントを確定する

`LiveMetricAccumulator.PrepareSave` は、記録中のファミリーが無いと、ロードしたか最後に確定したチェックポイントの文字列をそのまま書いていた。この場合、その保存は系譜上の自分の位置を残さず、続く保存とつなげなかった（E と F が該当）。

読めるチェックポイントがあれば、記録中のファミリーが無くても、保存ごとに新しい子（新しいID、親＝直前の確定）を確定するように変えた。記録していないファミリーは文字列のまま複製する。`throughTick` は変えないので、`throughTick < saveTick` となり、その値は「一部のみ」（Partial）になる。設計§3.5の「欠落以後は部分に落とす」に沿う。これまでの書き戻しでは、記録していない期間があっても代表値を「完全」と表示していた。

次の場合は従来どおり。読めない形式は原文のまま書き戻す（設計§3.5）。チェックポイントが無く記録も無いときは何も書かない。入れ子の保存・別スレッドの保存・保存フック停止中は確定しない。`_stopVersion` による判定は不要になったので削除した。

祖先は、後のtickの子が確定すると、既存の圧縮・アーカイブの対象になる。このため、プロフィールの増え方は、ファミリーを記録している通常の保存と同じである。

### 7.3 ゲーム内スナップショット：運んだだけのチェックポイントも同じ扱いにする

`RecordSave` は、新しいチェックポイントを確定した保存にしか `CheckpointKey` を付けていなかった。旧記録の対応付けも、チェックポイント自身のtickとの一致を要求していた。このため、古いチェックポイントを運んだセーブのスナップショットは常に白抜きだった。同じセーブのファイル取り込みは D に接続されるので、統計の種類によって表示が食い違っていた。単体テストで再現した（白抜きは `[-1,-1,-1]`、ファイル側は `[-1,0,0]`）。

修正は次のとおり。

- 記録側：保存したファイルが実際に含むチェックポイントのIDを `CheckpointKey` に記録する。この保存で確定したものか、確定しなかった場合は書いた文字列から `CheckpointJson.IdOf` で読んだものである。読めないデータでは記録しない。
- 判定側：`OfSnapshot` は `CheckpointKey` を、ファイル取り込みと同じ `At`（自身のtickなら exact、より後なら子孫）で扱う。
- 旧記録：`CheckpointKey` の無いスナップショットにも対応付けを広げた。スナップショットと同じ書込時刻・同じtick・同じキャンペーンの取込済みセーブファイルがあれば、そのファイルが含むチェックポイントで位置を決める。ファイルのtickは、チェックポイントを含むファイルのセーブ読取値（`SaveFile` 観測。圧縮対象外）から取る。2つのチェックポイントが同じファイルを主張する場合と、1つのファイルが2つのtickを持つ場合は、何も証明しない。

旧版で新しい記録を開くと、運んだチェックポイントの `CheckpointKey` は旧版の exact 要求を満たさない。そのため従来どおり白抜きになり、記録は保持される。

### 7.4 実セーブ6件での結果（`PrivateSixSaveChartLineageAcceptanceTests`、3件）

- 元のまま：線は従来どおり（`[-1,-1,1,2,3,3]`）。F の `SkipsOnlyOtherBranches` は false で、「別の分岐」とは表示しない。
- 旧スナップショット：6件のファイル時刻・tick で `CheckpointKey` の無いスナップショットを作り、プロフィールをディスクから読み直した。スナップショットのグラフは、ファイルのグラフと同じ線・白抜きになる。修正前は E・F が白抜き（`[…,-1,-1]`）。
- この版が書く場合：19:59のチェックポイントからロードし、何も記録せずに E・F を保存したときのチェックポイントを作った。E・F のコピーの `numericStatistics` だけを差し替えて取り込むと、F は E から続く（`[-1,-1,1,2,3,4]`）。19:59のセーブはライブラリに無いので、ファイルだけでは E の親が不明（白抜き）になる。ゲーム内でロード時に記録されるのと同じく、そのチェックポイントをプロフィールに加えると、E は D から続く。チェックポイントのグラフは6点になり、E・F の値は「一部のみ」になる。
- 修正を無効にした状態では、後の2件が失敗することを確認した。元ファイルのSHA-256・サイズ・更新時刻は前後で一致した。

### 7.5 既存のセーブについて残ること

- 既存の E・F は自分のチェックポイントを持たないので、この2件どうしはつながらない。F をロードして保存した次のセーブも、F ではなく、運ばれた古いチェックポイントの最も近い exact な祖先の点から引かれる。D から引かれ、19:59のセーブの記録があればその点から引かれる。その次からは1本につながる。
- 読めるチェックポイントが無く、記録中のファミリーも無いゲームでは、従来どおり何も書かない。

### 7.6 性能（同一ローカル環境、Release、7回の中央値、2回）

合成プロフィールで測った。10件ごとに5件前へ巻き戻す分岐を入れ、全点に旧スナップショットを持たせた。グラフ構築にかかった時間は次のとおり。

| 件数 | セーブ読取値のグラフ | スナップショットのグラフ |
|---|---|---|
| 100 | 0.58〜0.65ms → 0.73〜0.76ms | 0.55〜0.61ms → 0.71〜0.79ms |
| 3,000 | 12.0〜13.0ms → 13.8〜13.9ms | 14.5〜17.8ms → 23.8〜23.9ms |

グラフを開いたときに一度だけ、バックグラウンドで実行される。ゲーム中の保存処理では、記録中のファミリーが無い保存にも、記録中の保存と同じチェックポイントの書き出しが1回加わる。確定しなかった保存（入れ子・保存フック停止中）には `CheckpointJson.IdOf` の解析が1回加わる。

### 7.7 レビューで直した点

- 一時停止中の再保存：同じtickの b と、その子 c（一時停止中に保存し直したもの）は1つの状態としてまとめ、点は c で代表していた。このため、b をロードして続けた保存はこの点を祖先として見つけられず、さらに前の点から引かれていた。§7.2 で何も記録しない保存も子を作るようになり、この形が増える。そこで `NearestAncestors` は、exact な点を、同じtickの親の位置としても登録するようにした。`Same` が同じtickの親子を1つの状態とみなすのと同じ前提である。b のファイルを取り込んでいない場合も、c の親IDから同じように扱う。
- 旧スナップショットの対応付け：同じ書込時刻のファイルが2つのtickで読まれていると、そのファイルを無視していた。§7.3 に書いたとおり、何も証明しない（白抜き）ようにした。

## 8. 追補（2026-11-15）：チェックポイントのグラフで、系統の途切れより前の記録を残す（Issue #72）

**問題**：チェックポイントのグラフは代表チェックポイントから親を辿るだけだったので、親の欠落（その親を含むセーブを取り込んでいない）・重複・衝突で系統が途切れると、それより前の記録はグラフから消えていた。実セーブ6件では A（19:33）の点が出なかった（§3）。データは残っているのに、記録が消えたように見えていた。

**規則**（`MetricCalculator.CheckpointChartHistory` / `ReadingsBefore`）：

1. 系統の最初の点より前のtickを持つ、同じキャンペーンのチェックポイントを、系統の前に表示する。欠落した親を経て系統へつながる可能性があるからである。
2. それらの点どうしは、セーブ読取値のグラフと同じ規則で結ぶ（各チェックポイントは自分自身の状態＝exact）。証明できる親子の間にだけ線を引き、分岐は `ContinuesFrom` で表す。
3. 系統の最初の点は前の点とは結ばず、白抜き（`Unlinked`）にする。前の点のどれが祖先かは分からないからである。
4. 系統の最初の点と同じtick、またはそれより後のチェックポイントは祖先になり得ない。これらは別分岐として表示しない（従来どおり）。
5. 重複ID・衝突したチェックポイントは何も証明しないので表示しない（系統の辿り方と同じ）。
6. 値をアーカイブへ移したチェックポイントも、従来の系統の点と同じように、グラフを開いたときにアーカイブから値を読む。`SavedTick` も同じ規則で付ける。一時停止中に同じtickで再保存されたチェックポイントは、子孫側がそのtickを代表する（系統と同じ）。

途切れより前に分岐があれば、それらもすべて表示される。どの分岐が欠落した親へつながるかは分からないためで、セーブ読取値のグラフと同じ扱いになる。系統が途切れていなければ、グラフは変わらない。翻訳文は変えていない（白抜きの凡例は既存の文を使う）。

**実セーブ6件**：チェックポイントのグラフは A・B・C・D・E′ の5点になり、B が白抜きになる。`PrivateSixSaveChartLineageAcceptanceTests` の期待値を更新し、3件とも成功した（元ファイルのSHA-256・サイズ・更新時刻は前後で一致）。

**性能**（合成、10件ごとに5件前へ巻き戻す分岐、Release、9回の中央値、2回）：系統が途切れていない場合は変わらない（3,000件で 5.5〜5.8ms）。中央で途切れた3,000件では、2.6〜2.8ms（904点）から 10.0〜10.3ms（2,404点）に増える。表示する点が増えた分で、グラフを開いたときに一度だけ実行される。

**テスト**：`MetricChartLineageTests` に4件（途切れより前の点と白抜き、前の分岐どうしの線と後の別分岐の除外・衝突の除外、一時停止中の再保存と後のセーブの `SavedTick`、途切れのない系統は不変）、`MetricChartHistoryTests` に1件（途切れの前後のアーカイブ値がそれぞれの点へ戻る）を追加した。規則ごとに実装を1か所ずつ壊す変異（tickの条件、衝突・重複の除外、白抜き、アーカイブの判定と位置、`SavedTick`、同じtickの代表）を7通り試し、いずれもこれらのテストで失敗することを確認した。
