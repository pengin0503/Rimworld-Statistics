# Rimworld-Statistics — 数値統計拡張・基本設計（2026-11-07）

> **状態：設計ドラフト（実装・リリース変更なし）**。v1.0.0の仕様を維持し、次期拡張の構造、統計の意味、取得方法、保存、重複排除、表示、段階導入、検証条件を設計する。RimWorld 1.7での詳細なAPI・実セーブ照合および設計レビューを経て確定する。
>
> **前提資料：** [416項目の一次整理](2026-11-07-statistics-expansion-triage.md)・[元の416項目候補](2026-11-07-statistics-expansion-candidate-catalog.md)・[v1.0.0設計](2026-11-06-rimworld-statistics-design.md)・[1.7実現可能性調査](../../research/2026-11-06-rimworld-1.7-feasibility.md)。

## 1. 目的・範囲

### 目的

タイトル画面から、過去の全コロニーを横断して**数値によるゲーム内実績**を確認できるようにする。既存セーブの解析を先に拡張し、そこで復元できない出来事は将来のプレイから軽量に記録する。詳細な内訳・最高記録は許可するが、グラフ描画はしない。

### 一次整理の結果（変更しない）

| 分類 | 件数 | 方針 |
|---|---:|---|
| 維持 | 122 | 独立した候補として実現性を調べる |
| 統合 | 201 | 16の統合先を使用。表示する数字は必要なら複数残す |
| 保留 | 37 | 精度/負荷/互換性を実証するまで実装しない |
| 原則除外 | 56 | 次期実装対象から除外。原本には残す |
| 合計 | 416 | IDで追跡可能 |

**今回実装を検討する対象は122＋201＝323候補だが、323個のフック・テーブル・初回リリースの意味ではない。** 拡張は段階的に出す。保留・除外候補はレビューで再開可。既存の概要13数値、エンディング記録、コロニー同定は既定動作を維持する。

### 非目標

- グラフ、時系列チャート、録画、詳細な戦闘ログ、操作ログの大量保存。
- 全416項目の一括実装やすべての旧セーブでの全項目復元を保証すること。
- 旧セーブの書き換え、起動/セーブ処理の妨害、毎Tickの全マップ・全Pawn走査。
- これまでのv1コロニー・エンディングの意味を無断で変更すること。

## 2. アプローチ比較と採用案

| 方式 | 長所 | 制約 | 判定 |
|---|---|---|---|
| A. 既存セーブのスナップショット/履歴を解析 | 古いコロニーも対象。ゲーム中の追加監視が不要 | 消された過去イベントは復元不可。大きなXMLの読取り負荷 | **先行採用** |
| B. イベント発生時に数値だけ増分計上 | 撃破・加入・交易など詳しい実績を取得。毎Tick走査を回避 | 事後導入分しか取れない。重複・巻戻し対策が必要 | **第2段階** |
| C. 全てのイベントを生ログに保存して後から集計 | 定義変更の自由度が高い | サイズ・負荷・プライバシー・巻戻し管理のコストが高い | **不採用** |

**決定：A＋Bのハイブリッド。** 同じ種類のデータを複数箇所で独立計数しない。v1の4タブを維持し、数値の詳細閲覧画面を足す。

## 3. 値の契約と集計単位

### 3.1 全数値に必要なメタデータ

各統計をIDで識別する（例 `H-001` は**仕様参照ID**、ランタイムでは安定した内部メトリクス名を別途定義）。表示名、単位、取得ソース、演算種別、対応バージョン、DLC条件、集計粒度、既存セーブでの復元可否、優先度、欠損の意味を定義する。

| 属性 | 候補 | 説明 |
|---|---|---|
| 種別 | `Sum / Max / Min / Snapshot / WeightedAverage / Derived / UniqueCount` | 異なる演算を単純加算しない |
| 粒度 | `Colony / Pawn / EventCategory / DLC` | 最終的な全コロニーの合計は適用可能な場合のみ |
| ソース | `VanillaCounter / SaveHistory / SaveSnapshot / LiveAggregate` | 一つの観測値の来歴が分かる |
| カバレッジ | `Complete / Partial / SnapshotOnly / Unknown` | **Unknownを0として表示しない** |
| 時刻 | ゲーム内tick＋実世界UTC（利用可能な場合） | 経過ゲーム内日数とプレイ時間を混同しない |
| 特殊条件 | DLC、開発モード、ゲーム版、MODによるDef | 確実に除外・判定できる条件だけ使う |

`Complete` は**この統計の必要範囲の記録がそろった**という意味であり、古いセーブをひとつ読めたという意味ではない。ゲーム開始前からのイベント統計は、拡張導入前には原則 `Partial`。途中のセーブに見つかった数値は `SnapshotOnly`。値自体の0と「未記録」は表示上も保存上も別状態とする。

### 3.2 時系列や差分の取扱い

- 履歴の**平均値**は、記録間隔が等しいことを確認し、期間と欠測を考慮して計算する。複数のセーブの平均をさらに平均することはしない。
- 極値・到達日数・継続日数は、履歴が残る範囲での**観測記録**。実際の瞬間最大/最小と取り違えない。
- 後半だけのセーブしかない場合、履歴の先頭時刻と期間に根拠がなければ初回到達値は `Unknown`、または `Partial` で示す。
- 所持品・研究・勢力関係は「最後の観測」「観測範囲の最大」と表記し、過去の累計生産数などを状態差分から推測しない。
- `R-*` のランキングは確定したコロニー別値を再利用し、新たなゲームイベント監視はしない。割合・率は有効な分母とサンプル数を表示する。

### 3.3 コロニーの統合と枝分かれ

v1の `CampaignMatcher` による同一コロニー判定を引き継ぐ。ただし**同一コロニー ≠ 同じ進行経路**。一度セーブを戻して別の進行をした場合、2分岐のイベント累計を単純合算すると水増しになる。

- **v1既存カウンター・エンディング：** 今の `StatsCalculator` / `EndingLedger` の規則を変更しない。
- **新規の単調累計：** 各セーブの進行経路内に持つ累計値を基本とし、保存観測をコロニーに集約した後、**代表となる1分岐**を選んで値を読む。異なる分岐の累計同士を合計しない。
- 代表分岐の暫定選定順は、最大の有効ゲーム内tick→最新の保存時刻→安定した観測ID。巻き戻し・分岐が見つかればUIに「分岐あり」と表示する。**利用者が別の分岐を選択する画面は後段階**。
- 撃破や加入などを「人生で遭遇したすべての分岐も含める」方式は、同じイベントの再演と別イベントを識別できる保証がない。既定では採用しない。
- 「いったん到達した最良記録」は `Max` 系として分岐横断で維持できる。平均や合計は代表分岐上で計算し、混合しない。

**設計レビュー時の要確定事項：** 代表分岐方式と「すべての試行のユニークイベントを加算」のどちらを将来的な優先目標にするか。現時点は前者を安全な初期案とする。

## 4. データ取得の設計

### 4.1 Phase A：履歴・既存カウンター（先行）

`SaveReader` / `RecordsCodec` のストリーミング解析を拡張し、確定済みの系列を**必要な数値要約だけ**に圧縮する。

現行調査で存在を確認した履歴系列：
`Wealth_Total`、`Wealth_Items`、`Wealth_Buildings`、`Wealth_Pawns`、`FreeColonists`（実セーブでの版別再照合を実施）。心情・囚人等の系列は名称・欠測・記録間隔を実データで確認できるまでは実装確約しない。

| 実装候補 | 元のID | 算出と制約 |
|---|---|---|
| 資産の内訳別の最高・最終額 | H-001〜003 | 3系列の有効値から。系列の欠落時は0で埋めない |
| 資産平均・開始値・純増・最高日 | H-004, H-006〜008 | 時刻・記録間隔・開始点の存在を確認 |
| 資産の最大増加/減少額 | H-009〜010 | 定義した観測窓で差分算出 |
| 自由入植者の平均・最小値 | H-020〜021 | `FreeColonists`。対象が殖民者と同一かラベル明記 |
| クエスト成功・失敗 | S-001 | `questManager` の永続クエスト結果が利用可能な範囲で集計（保持状態の実証要） |
| クエスト成功率 | S-002 | 対象母数/無効・キャンセルを先に定義 |

**シリアライズするのは系列そのものではなく、対象期間、サンプル数、最小/最大/合計（必要なら差分と初回到達tick）、ソース情報等の小さな要約。** 閾値を後から変える場合、元セーブが残っていれば再解析する。元セーブが消えていれば旧要約の範囲を超えた再計算はできないため、推定値を捏造しない。総資産 `Wealth_Total` の先頭値ビット列はコロニー同定に使うので変えない。

### 4.2 Phase B：静的状態（実セーブ照合後）

- 研究完了・取得可能な状態（`S-012` 等）、装備・武器の保有状態（`S-017` 等）、所持品・拠点設備数などを抽出候補とする。
- `maps` を巨大な `XElement` として全展開しない。必要な子要素だけ `XmlReader` で通過し、未知のMOD領域を原則スキップする。
- セーブ内のPawn/Thingの多重参照、キャラバン・マップ間移動、禁制品/装備中/地面の所持品の範囲を定義する。読み取れない場合は当該指標だけ `Unknown` にして、ほかの統計を壊さない。
- 技術段階などのDef名は、RimWorld本体を起動しないインポート処理で**DefDatabaseへアクセスしない**。必要な対応表が定義できないものは後回し。

### 4.3 Phase C：新規イベント累計

ゲーム内で成果が確定したタイミングでのみ、軽量なカウンターを更新する。

| 基礎記録 | 将来の数値出力例 | 参照候補 |
|---|---|---|
| `PawnMembership` | 初参加人数、勧誘、再加入、離脱、出生 | P-001〜003、N1-C-003〜004 |
| `PawnDeath` | 死者、死亡原因、戦闘による死亡 | P-004、B-021 |
| `CombatKill` | 敵撃破、種類別、手段別、入植者別 | B-001、N1-B-006、N5-B-001〜005 |
| `WorkCompleted` | 製作数、品質別、収穫量、採掘量 | W-001〜006、N3-W-001〜005 |
| `TradeCommitted` | 売上、仕入、取引回数、品目別 | T-001〜008、N4-R-001〜003 |
| `ResearchCompleted` | 完了数、完了日、最速研究 | Q-001〜004、N5-M-004 |
| `QuestResolved` | 成功/失敗、所要日数、種類別 | S-001〜002、Q-006 |
| `CaravanLifecycle` | 遠征回数、帰還、総距離 | Q-008〜010 |

これは**概念上の記録単位**であり、RimWorld側にこの名称のイベントやAPIが存在すると確認したものではない。各記録のフック対象・頻度・署名・防止条件は版別の検証をしてから決める。高頻度の戦闘・作業は必要最小限の確定イベントとし、危険性の高い37の保留指標を無理に取り込まない。

### 4.4 Phase D：DLCとランキング

- DLCの有効状態を確認したうえで `Royalty / Ideology / Biotech / Anomaly / Odyssey` の計測アダプターを段階的に提供。
- 各DLCがない環境、DLCはあるが無効な環境、MODで同等のイベントが追加された環境を区別する。
- 最速クリア、最大撃破数、バイオーム別生存日数等のランキング・派生表示は、必要な基礎統計が揃ったときだけ表示。
- 保留37件と原則除外56件はこのPhaseに自動的に含めない。

## 5. 永続化と「巻き戻しても増えない」方式

### 5.1 v1資産を保護する

現行の `Profile.CurrentSchemaVersion = 1`、`SaveReader.Version = 3`、`GameComponent_RimworldStatistics.dataVersion = 1` を確認済み。新しい値を無造作に既存の `ObservedValues` へ加えても、現在の `ProfileMutations.Dominates` が新統計を知らないまま古い `SaveObservation` を削除するため、**消失・誤集計の恐れがある**。これは最優先で防ぐ。

- v2相当のプロファイル読み込みは **旧v1を移行・新旧不明フィールドを安全に保持** する設計とし、ロールバックの可否を明示する。新しいバージョンを書いたあと旧MODで新ファイルを上書きしないよう現在の新スキーマ読取り専用制御を利用する。
- インポート結果が変わる段階で `SaveReader.Version` を更新し、現存ファイルだけ再解析する。**現存しない元セーブや過去の上書き履歴は再構成不能**なら未知状態で維持する。
- 初期段階では、追加の履歴/スナップショット情報が付いた観測を `Dominates`/枝刈り処理で削除しない安全側の実装を優先。削除最適化は**新しい全統計と識別証拠を保存しても等価**と証明した場合に限る。
- `ProfileStore` の一時ファイル、3世代バックアップ、外部変更検出、破損時の退避、`ProfileSession` の単一シリアル化を維持する。更新前のバックアップを残す。

### 5.2 保存単位

- `SaveObservation`: 旧セーブの特定時点の値と `HistorySummary`、観測範囲、ソース・欠測状態。
- `LiveCampaign`: v1既存の `Max`・`Latest`を維持し、新統計は別の `MetricSnapshot` 群として保持する（古いJSONフィールドを壊さない）。
- `GameComponent_RimworldStatistics`: 次期版で`dataVersion`を拡張し、**イベント別の累積カウンター、出所、計測開始tick、分岐を判別できるチェックポイント情報**を保存候補とする。旧バージョンの`campaignId`と`lineageEndings`はそのまま扱う。
- `MetricRegistry`: 内部ID、集計規則、単位、ソース、表示名の正規定義。統計間の派生計算は`MetricCalculator`で扱う。
- 拡張データに欠損/部分記録があれば、全Profileをエラーにせず各値を `Unknown/Partial` とする。

### 5.3 イベント確定と再ロード

**推奨初期ポリシー：** ゲームの新しいイベント累計はメモリ内に反映し、**セーブが正常に確定したときに**分岐のカウンター写しをプロファイルへ確定する。単にイベントが発火しただけで、まだセーブされていないデータを永続的な通算値として加算しない。これにより、古いセーブの再ロードを単純な加算として扱う問題を避ける。

- 保存時には、進行系譜の親チェックポイントと新しいチェックポイントIDを生成/保持する案を採る。**具体的にどの`ExposeData`/セーブ完了フックでIDを確定するかは、保存失敗・自動セーブ・ロードを含む実機検証で決定する。**
- タイトル画面への復帰、ゲーム終了、セーブ直後の失敗に対応し、「成功したチェックポイントだけが通算の根拠になる」ようにする。
- コロニーの統合は`CampaignMatcher`、枝分かれの対応は`checkpointId`と`parentCheckpointId`を持つ独立した層で行い、コロニー識別の仕様を混ぜない。
- 既存のエンディング処理はセーブされず終了するケースを扱うため、**v1の即時記録を維持し、この原則の例外**とする。将来の例外は機能ごとに別途設計する。
- 同じセーブを何度読み込んでも、同じチェックポイントを重複登録しない。コピーされたセーブ、上書き、分岐、MODを一時削除した場合の再開はテストで判断する。

## 6. UI設計：数字だけで閲覧する

v1の既存4タブ（概要・エンディング・コロニー・取り込み）とその情報を残したまま、**「詳細統計」タブ**を追加する案とする。

1. 画面上部：集計範囲 **全コロニー / 個別コロニー**。除外指定の反映状況を明示。
2. カテゴリー：資産、人口/心情、戦闘、生活、製作、交易/研究、遠征、DLC、ランキング。統合16グループは内部構成であり、16個のタブを作るわけではない。
3. 各行：**項目名 / 数値・単位 / 記録範囲 / 取得状態 / 最高コロニー**（該当するとき）。種類別内訳は折りたたみで表示。
4. 検索・並べ替え：項目名、コロニー名で絞る。大量の行を常時生成せず、必要な表示領域だけ描画する。
5. **未記録、部分記録、推定、該当DLCなし**を区別し、ツールチップに出所・計測開始日・対象コロニー数を表示する。
6. 0は明確に取得できた場合にだけ表示。分母が0の比率、母数不明の割合は「—」と理由を表示。
7. 日本語・英語を両方用意。独立キーの重複、長いMOD由来Def名、数字桁あふれをテストする。
8. 描画処理でセーブ走査やJSON読込みを実行しない。`ProfileSession.GetView` 等の非同期キャッシュを利用し、更新でキャッシュを破棄する。

画面構成（テキストモック。グラフなし）：

```text
[概要] [詳細統計] [エンディング] [コロニー] [取り込み]
[対象：全コロニー▼] [検索：______] [分類：資産▼]

総資産（最高）       925,790       確定/33コロニー
アイテム資産（最高）  ...           旧セーブ由来/対象27
建築物資産（最高）    ...           旧セーブ由来/対象27
平均入植者数          ...           記録あり/対象20
敵撃破総数            —             未記録（導入後に計測）
```

上の数値925,790は以前の調査例に過ぎないため、実装時にはサンプル文言と実データを混同しない。

## 8. リリース分割と受け入れ基準

### A：既存セーブ由来の数値拡張（最優先）

### D：DLC・派生ランキング・残りの優先候補

## 9. 未解決の判断と次に行う調査

1. **分岐の定義（最重要）：** 代表分岐方式を正式化するか、何を「通算」とするか。初期案は分岐横断合算をしない。
2. **数値要約に必要な最小系列情報：** 資産増加率・年平均・継続期間・中央値を復元するために何を保持するか。原本が消えても必要な数値だけは保全する。

6. **計測開始の境界：** MOD導入後初回ロード、最初の正常セーブ、ゲーム開始から記録した場合のカバレッジを区別する。
7. **優先順位：** 323対象候補は継続的に取得可能性と有用性で選別。各リリースで独立に完了する小さな範囲だけ確定する。
