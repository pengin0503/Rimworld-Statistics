# RimWorld Statistics — 暫定設計仕様（v0.1）

- 作成日: 2026-11-06
- 状態: Draft / 検討用。実装承認・仕様確定を意味しない。
- 対象: RimWorld 1.7 を第一対象とする（実際のゲームAPI、DLC、他MODとの互換性は実装前に再検証）。
- 対象リポジトリ: pengin0503/Rimworld-Statistics
- この段階の成果物: 設計文書のみ。C#、XML、パッチ、ビルド設定、ゲーム内実装は追加しない。

## 1. 背景・目的

ユーザーが求めるのは、セーブを1つロードして参照する「コロニー履歴」ではなく、**タイトル画面から全プレイの通算統計を閲覧できるプロフィール型の記録MOD**である。

最優先の例:
1. これまでプレイしたゲーム内日数（全コロニーの合算）
2. 惑星から脱出した回数（成功回数と脱出人数を区別）
3. これまでの合計資産（意味を明記したコロニー横断の合算）

目指す体験:
- タイトル画面の「通算統計 / Statistics」から、セーブを読み込まずに数値を見る。
- 複数のコロニー・異なるセーブファイルの記録を横断して集計する。
- MOD導入以前の既存セーブも、取得できる範囲で初回取り込みする。
- 以後の記録は、セーブの削除や古いセーブのロードで安易に失われない。
- パフォーマンスと他のセーブ管理MODとの共存を重視する。

## 2. 用語・集計単位

- **セーブ（save snapshot）**: ある時点の .rws ファイル。自動保存・手動保存・同名別名保存を含む。
- **コロニー／プレイスルー（campaign）**: 同一の開始状態から継続しているゲーム系列。通常は複数のセーブファイルを含む。
- **全体プロフィール（profile）**: コロニーを横断する通算記録。ゲーム本体の各セーブとは独立して保持する。
- **観測値（snapshot）**: セーブに保存されている時点の値。過去の全イベントを表すとは限らない。
- **イベント（event）**: 脱出成功など、一度起きた事実として記録する対象。
- **確度／対象期間（coverage）**: どの期間・どの方式で数値が取得されたか。未取得と0件は別物。

**禁止する集計**: セーブファイルを1件ずつ独立したプレイスルーとみなし、日数や資産を単純加算すること。オートセーブが多数あるだけで数値が水増しされる。

## 3. 表示する統計（優先順位・暫定定義）

| 優先度 | 統計 | 表示例 | 暫定的な算出・記録方法 |
| --- | --- | --- | --- |
| P0 | 通算ゲーム内経過日数 | 1,842日 | 各コロニーの観測済み最大経過ゲーム時間を合算。重複セーブは加算しない。内部はティック等の精度を維持し、最後に日数表示へ変換する。 |
| P0 | 惑星脱出成功回数 | 7回 | 達成した脱出／エンディングイベントを一意に記録し通算。結末の種類は分類できるようにする。 |
| P0 | 惑星脱出人数 | 23人 | 実際に脱出した入植者等の人数を可能な限りイベント単位で記録。成功回数とは別指標。 |
| P0 | 記録資産の合算 | 12,450,000 | 各コロニーで最後に確認できた資産の合計。これは「歴史上で獲得した全資産」ではないことをUIで明示。 |
| P0 | 記録したコロニー数 | 24 | 同一コロニーの重複セーブは1件として計上。 |
| P1 | 歴代最高資産 | 2,830,000 | 単一コロニーで確認した資産の最高値。 |
| P1 | 最長存続コロニー | 423日 | 各コロニーの最大経過日数の最高値。 |
| P1 | 死亡入植者の累計 | 73人 | 取得可能な履歴または導入後のイベントを利用。重複計上を防ぐ。 |
| P1 | 襲撃回数の累計 | 562回 | 取得可能な既存履歴または導入後のイベントを利用。 |
| P2 | 追加統計 | 研究、建設、戦闘、交易など | 正確な定義・取得可否・負荷を調査してから追加。 |

※ 上記の数値はすべて架空のUI例であり、ゲームデータからの実測値ではない。

### 集計定義に関する重要な注意

- 「通算ゲーム内日数」の暫定定義は**コロニーごとの最大到達日数の合計**とし、ロードや巻き戻しで同じ日を再プレイしても原則重複計上しない。「実際にシミュレートした延べ日数」とは異なる。必要であれば別指標として定義する。
- 「累計資産」は多義的。v0.1では**各コロニーの最終観測資産の合算**を仮採用し、別途「各コロニーの過去最高資産の合算」を候補とする。これらは生産総額・稼得額ではない。
- 最終観測資産はゼロでもあり得るが、未確認（Unknown）をゼロに置き換えない。
- DLC別・エンディング別に「脱出」と見なす条件は調査項目とする。船での脱出、貴族エンディング、アーコネクサス等を同一指標にまとめるかは明示的に決める。
- 過去データの読み取りではイベントの完全な復元を保証しない。実際に保存された状態・履歴があるかを検証する。

## 4. タイトル画面のUI（暫定）

- メインメニューに「通算統計」ボタンを追加（可能なら他MODや既存UIを邪魔しない配置）。
- 開くと概要カードを表示: ゲーム内日数、脱出成功回数、脱出人数、資産合算、コロニー数。
- 「詳細」ページ: P1統計、記録開始日、対象データ数、計測対象期間／欠損の説明。
- 「コロニー別」ページ: 各コロニーを選択して観測済みの最高値・最終値・記録状況を確認。これは主目的ではなく全体統計の根拠を確認する補助機能。
- 確認済み、推定／部分復元、未取得をUIで区別し、取得できない値を0と偽装しない。
- 初回取り込み中は進捗、キャンセル、読込失敗数を表示。タイトル画面の統計閲覧そのものは集計済みデータを読むだけにする。
- 日本語UIを初期対象とし、翻訳キーを前提に英語追加可能な構造を想定。

## 5. 記録・永続化モデル（設計方針）

- 全体プロフィールは各 .rws と独立したローカルデータとして保存する。既存セーブが消えても、取り込み済みの履歴を残す。
- コロニー単位の識別子（Campaign ID）と、記録値の出所（実行中の観測／セーブからの復元）を保持。
- 新規ゲームには安定したCampaign IDを割り当てる方法を検討する。既存セーブにIDがない場合は、取得可能なセーブ内情報と確認手順で同一コロニーを推定し、誤統合を避ける。ファイル名だけを識別子としない。
- 同一系列の別名保存・オートセーブは、最大経過日数やスナップショットの時点を突き合わせて統合する。
- 分岐セーブ（過去に戻して別の展開を進めたもの）については、同一コロニーとしてまとめる場合と別プレイスルーとして数える場合を区別できる設計とする。自動判定できない場合の手動統合／分離を将来検討。
- イベント型指標は一意なイベントID等によって再読み込み時の二重登録を防ぐ。イベントの再現・別分岐・クラッシュ直前の再実行は仕様検証が必要。
- データには形式バージョンを持たせ、原子的保存・バックアップ・破損時の復旧・マイグレーション方針を用意する。
- できるだけ頻繁なディスク書込みを避け、変更分の反映タイミングを定める。
- 原則ローカル保存とし、外部通信やユーザーアカウントは不要。
- 保存先は標準のユーザーデータ領域を優先。詳細なパス・形式（JSON等）は技術検証後に決める。

## 6. 既存セーブの初回取り込み

1. ユーザーが明示的に取り込みを開始する（初回案内を用意）。対象セーブの件数を表示。
2. 安全に読める .rws を列挙し、セーブをゲームとしてロードせずに取得可能なメタデータ・統計値を抽出。
3. 同一コロニーに属する複数セーブを推定し、重複を統合する。曖昧なケースは要確認状態にする。
4. 復元できるスナップショット指標のみ確定し、イベント型指標はセーブに根拠が存在する場合だけ追加。
5. 失敗したファイル・理由・取り込み対象範囲を記録し、再試行可能にする。
6. 再スキャン時は既存のCampaign IDと登録済みイベントを照合し、二重加算しない。

過去のセーブに記録がないイベント、削除済みセーブのみが保持していた情報は復元不能な場合がある。履歴統計の所在、セーブXMLの形式、MOD追加項目の互換性はコード実装前の検証事項とする。

## 7. MOD導入後の継続計測

- ゲームの既存の状態変化やイベントをなるべく低頻度・低侵襲で観測し、P0から確実な指標を記録する。
- 脱出などの一度限りのイベントは、イベント成立時点で一意に記録できる方法を調査する。
- ロード、セーブ、オートセーブ、タイトル画面への復帰、終了、クラッシュ復旧を考慮する。
- 過去セーブに巻き戻しても確認済みの全体プロフィールを単純に巻き戻さない。
- ただし失敗していないイベントの再試行を新しい成功として誤計数しない。分岐したプレイの扱いは仕様として確定させる。
- 計測不能な状況は黙って成功扱いにしない。無効・未対応・未確認のステータスを残す。

## 8. パフォーマンス・互換性・安全性

- 通常プレイ中は毎ティックの全件スキャンを行わず、イベント駆動・低頻度サンプリングを優先する。
- タイトル画面の表示は集計済みインデックスを読み、起動のたびに全 .rws を走査しない。
- 初回・手動再スキャンは別処理とし、件数が多くても画面を長時間固めない設計にする。
- RimWorld 1.7 を第一対象。ゲーム本体・DLCの実API対応は調査のうえで確定する。
- RimSaves、More Autosave Slotsなどの既存セーブ管理MODと共存する方針。セーブ／ロード画面の置換やセーブファイル内容の破壊的編集は避ける。
- Harmonyは必要最小限に留め、標準APIで実現可能な部分は標準APIを優先する。
- 読込み対象セーブは読み取り専用。破損セーブ・未知のMODデータが混在しても他のセーブの読み込みを妨げない。
- セーブやプロフィールの削除・統合など不可逆な操作は黙って実行しない。

## 9. v1候補の受け入れ条件（実装前に確定）

1. タイトル画面だけで全体統計が表示でき、どのコロニーもロードする必要がない。
2. 1つのコロニーに手動セーブ10件・オートセーブ10件があっても、ゲーム内日数・資産が20倍にならない。
3. 別の2コロニーを含む場合は、それぞれの指標を定義通り合算できる。
4. 同じファイルを再取り込みしても通算値が増えない。
5. 古いセーブをロードしても既存プロフィールが不正に減少・重複増加しない。
6. 既存セーブの解析に失敗しても、その元ファイルを書き換えず処理を継続できる。
7. イベントを復元できない場合、「0回」ではなく未確認または一部のみの計測だと分かる。
8. 取り込み済みセーブを削除しても、全体プロフィールの記録は維持される。
9. RimSavesとMore Autosave Slotsを併用する構成で、既存の保存・読込機能を妨げない。
10. 通常プレイに目立ったTPS低下を起こさない（定量的な許容値はベンチマーク前に決定）。

## 10. 未決定事項・実装前の調査

- ゲーム内日数を「最大到達日数の合算」以外の定義でも記録するか。
- 「合計資産」は最終観測資産の合算・過去最高資産の合算・真の獲得総額のどれを主指標とするか。
- 脱出成功の定義と各DLCエンディングの分類・記録ポイント。
- 既存セーブから実際に取得できる履歴統計の範囲と信頼度。
- 同一コロニー識別と分岐セーブの扱い。自動判定の誤統合時の修正UI。
- 複数PC・Steam Cloud・プロフィールファイル競合への対応方針。
- P1以降で何を最優先にするか、ゲーム本体の統計と新規収集指標の重複整理。
- 保存データをユーザーがバックアップ・エクスポート・初期化する操作の必要性。
- 公開時に適切なライセンス・依存MOD・対応バージョン表記。
