# Implementation-ready plan: post-v1.4 statistics from five private save observations

**Status: approved only for future implementation; this PR implements nothing.**
Base: `main@f6890ee626bceb087693136a304333ce089d926c`, catalog **331 + 84 = 415**. Source evidence: [sanitized five-save audit](../../research/2026-11-10-post-v1.4-private-five-save-audit.md). Do not use the earlier PR #79 five-save checkpoint chain as the test data for this new set. All originals remain private, read-only, and unavailable in public CI.

## Invariants that every implementation must preserve

1. **Scope:** add only meaningful **cross-colony** aggregate/rank/record features or stronger inputs feeding them. Do not introduce an extra current/latest-from-one-save metric merely because an XML element exists. Distinguish lifetime event accumulators, representative saved-state sums, observed historical peaks and partial interval evidence.
2. **One colony, one contribution:** use `CampaignMatcher.BuildColonies` and `CheckpointSelector.Select` to choose an evidence-supported representative; never add sibling branches, ancestor and child saves, or several copies of one checkpoint. A shared fingerprint is **grouping evidence**, not a direct lineage edge.
3. **Missingness:** preserve observed numeric zero distinctly from Unknown, Partial, SnapshotOnly and NotApplicable. `continuous` since a nonzero `sinceTick` never proves whole-history completeness. Missing family metrics cannot automatically become zero. DLC N/A requires an explicit saved requirement comparison.
4. **Compatibility:** no deletion or meaning change of any existing 415 key, `MetricKeys`, revision, profile field, checkpoint JSON v1, saved source type or provider stable key. Keep v1.4.0 release unchanged. A new reader version is allowed **only in a future implementation PR**, with once-only safe reimport and failed-reread preservation.
5. **Privacy:** original .rws, profile, full MOD list, pawn/campaign/checkpoint IDs and hashes are not fixtures, logs, CI artifacts or PR attachments. Publish only synthetic fixtures or aggregated anonymous verification status.
6. **Performance:** no per-tick full pawn/Thing walk. Any historical XML expansion must use streaming, bounded counts/depth/string length and fail-closed behavior. Benchmarks before optimizations, equivalent values after.

## Exact implementation surfaces and proposed contracts

### Stage 1 — missingness and full leaderboards (P0-A, P0-B)

- Source: `Source/RimworldStatistics.Core/Stats/{MetricRegistry,MetricDisplayPolicy,MetricCalculator,CrossColonyCatalog,CrossColonyAggregator}.cs`.
- UI: `Source/RimworldStatistics/UI/{DetailsTab,OverviewTab,ColoniesTab}.cs`, Japanese/English keyed XML.
- Tests: `Tests/RimworldStatistics.Core.Tests/{CrossColonyAggregationTests,NumericAggregationTests,NumericRankingTests,ExperimentalDisplayTests,ExperimentalEvidenceTests,NumericProfileTests}.cs`.
- Represent a breakdown result as: stable Def/category key, aggregated **quantity in source unit**, optional rank/holder (stable tie), captured colony count, applicable target count, `MetricCoverage`/evidence, measured contributing colony keys and their respective quantities. Avoid persisting raw source item/Pawn IDs or a new incompatible schema. The existing top-one derived row remains unchanged.
- For each selected independent colony, take **one** representative `NumericRow` for that source definition. If a source is absent/unknown, record missing **as missing**, not as a zero contribution. For each Def, sum measured compatible breakdown quantities **once per colony**; do not compose local winner identities. Compare each complete `by` total against its parent numeric scalar with the `CrossColonyAggregator.TopType` tolerance/semantics and retain `Partial` if totals do not reconcile. Reject mixed units/revisions or explain them as separate cohorts. The `FamilyState.By` 4096-key cap, Unknown bucket and truncated source always force incomplete-result labeling.
- Proposed presentation: existing `cross.top.*` summary, expandable/paginated entire descending ranking (including ties and known zero when meaningful), per-Def contributing colonies and measured values, share only when denominator is actually complete. Do not expose a misleading overall 100% for partial contributors.
- Diagnostic UI: show row source, acquisition gate/revision, sampled `Targets/Valid`, semantic `Coverage`, saved capture period and whether the necessary DLC was in the **saved** inventory. Do not guess `NotRecording` from an absent entry alone; use explicit metadata if available. Do not expose saved XML IDs.

### Stage 2 — safe historical backfill inputs (P0-C, P1-A–D)

- Reader: `Source/RimworldStatistics.Core/Reading/{SaveReader,HistoryMetricReader,HistoricalFactionSnapshotReader,HistoricalHomeMapReader}.cs`; add **separate bounded** validated readers where needed, feeding existing `MetricObservation` with save alias/provenance. Existing snapshot keys defined by `{ResearchStateSnapshot,RosterSnapshot,StockSnapshot,FacilitiesSnapshot}.cs` are the target; do not fabricate new event families.
- Runtime semantics reference: `Source/RimworldStatistics/SavedStateMetricReader.cs` (research uses live `DefDatabase<ResearchProjectDef>`; roster enumerates Pawn and filters; stock traverses holders plus gear and ThingID; facilities inspects `CompPowerPlant.PowerOutput`). For old saves, this game API is **not accessible** to offline `SaveReader`: either use version-matched proven Def metadata or return Unknown/Partial. Do not equate raw tags with live `Thing` classification.
- Research XML: `game/researchManager/progress/{keys,values}`, matched pair counts (123/123 in this sample). Need exact active `ResearchProjectDef` cost and finish semantics; a positive progress entry is not a finished-project assertion. Project identity can survive MOD differences only if proven. Snapshot metric `research.snapshot.finished` must be marked Partial on incomplete Def coverage and not called historical event count.
- Roster XML: `game/maps/li/things/thing` and saved world/holder pawn indices; map Pawn tags are **not** free colonists. Validate player faction, prisoner/guest ownership, kind/health, dead/world/caravan state, no duplicate ThingID across indexes. An unsupported nested source means Partial.
- Stock XML: spawned `things/thing` and nested contents. Include stackCount and ownership; avoid counting the minified shell plus contained object, equipment twice, hostile gear, or destroyed Things. Use bounded recursion + ID sets. Do not classify items by raw Def prefix when the corresponding mod/DLC Def semantics are unavailable.
- Facilities XML: `game/maps/li/mapInfo/parent`, world-object owner, `things/thing` with component state. Existing partial map backfill should not be replaced. A generator Def alone cannot establish *running* state; require saved working output/electric status equivalence.
- Medical/wealth: saved live conditions versus actually completed operation events; history recorders' stored series versus full lifetime accumulation. Preserve the correct provenance and intervals.
- Import: `Source/RimworldStatistics.Core/Import/{ImportEngine,SaveFileIndex}.cs`, `Profiles/ProfileMutations.cs`; upsert checkpoint and SaveFile/SaveSnapshot observations atomically and repeat-safe. Increment `SaveReader.Version` only with a code change, migrate via safe re-read, reject malformed/oversized input without discarding last good data, and avoid altering checkpoint v1.
- Tests: `NumericSaveReaderTests,NumericSnapshotResearchTests,NumericSnapshotRosterTests,NumericSnapshotStockTests,NumericSnapshotFacilitiesTests,HistoricFactionBackfillTests,HistoricalHomeMapBackfillTests,NumericImportTests,OriginalWealthHistoryTests,OpenIssueRegressionTests`. Use synthetic XML with explicit expected values plus opt-in original-file acceptance outside public CI.

### Stage 3 — performance and compatibility (P2)

- Candidate hotspots **not yet proven**: `ProfileMutations.NeedsRead` linear `Any` for each imported file, repeated profile observation searches, full XML hashing/scanning, growing breakdown dictionary/group operations, and new 12k+ map Thing traversal. Profile comparison must be deterministic and preserve alias/mtime/revision logic. Existing `CrossColonyAggregator` filters its index to needed keys; retain this optimization.
- Benchmarks: `tools/SaveImportBenchmark`, `tools/ProfileBenchmark`, `tools/PrivateSaveProbe`, optional read-only private acceptance tests. Collect 5-save cold and warm measurements **of the production .NET reader**, at least 55 real-save imports when available, and 100/500/1,500/3,000 synthetic profiles. Report medians/p95, elapsed, allocations, working set, persisted bytes; check results identical and original SHA+size+mtime identical. Do not compare non-equivalent CI hosts.
- Game-specific acceptance under #63: same game build/MOD list/map/seed/speed and load, five matched TPS windows, <=2% median TPS degradation target; ten paired saves, <=50 ms or <=5% overhead target. Room/pollution optimized readers require `mismatches=0 errors=0`.
- For differing MOD/DLC, check saved inventory per save and metric `RequiredDlc`; missing provider => preserve old descriptors/history, not zero; changed Def semantics => Unknown/Partial rather than mixing categories. Validate UI and data after both new-v1.4.0 and legacy profile load, with no category/key loss.
