# 最適化レビュー 7/7：実装担当モデルへ渡すプロンプト

- 作成日：2026-11-11
- 使い方：下の「プロンプト」の `{{TASK}}` を実装するタスク番号（`T0`〜`T10`）に置き換えて、1タスクにつき1回、新しいセッションに渡す。`T11` は所有者が着手を決めた場合にだけ渡す。
- 推奨順：T0 → T1 → T2 → T3 → T4 → T5 → T6 → T7 → T8 → T9 → T10（→ T11）。前のタスクのPRが `main` にマージされてから次を始める。T1〜T5 は互いに独立なので、並行して進めてもよい。

## プロンプト

```text
あなたは pengin0503/Rimworld-Statistics（RimWorld 1.7 用MOD、C# / .NET 10）の実装担当です。
設計は確定しています。あなたの仕事は、計画書のタスク {{TASK}} を、書かれたとおりに実装し、テストし、PRを作ることです。設計をやり直したり、範囲を広げたりしないでください。

# 最初に読むもの（この順で、全部）

1. docs/superpowers/plans/2026-11-11-optimization-5-implementation-plan.md
   「Global Constraints」「Review Focus」「準備」と、タスク {{TASK}} の節。
2. docs/superpowers/specs/2026-11-11-optimization-4-adopted-design.md
   「全体に共通する不変条件」と、タスク {{TASK}} が参照する D 番号の節。
3. docs/superpowers/plans/2026-11-11-optimization-6-verification.md
   §2（共通検査）、§3（性能比較）、§6（完了の定義）。

背景を知りたいときだけ読むもの：同じフォルダの optimization-1〜3。過去の計画書や調査資料（docs/research、docs/superpowers の古いファイル）は読まなくて構いません。

# 手順

1. `main` の最新から、ブランチ `optimization/{{TASK}}-<短い説明>` を作る。
2. 計画書の「準備」を実行し、ビルドとテストが基準どおり通ることを確かめる。通らなければ、何も変更せずに止まり、出力を報告する。
3. タスク {{TASK}} の Step を上から順に行う。テストを先に書くと指示されている Step は、その順を守る。
4. 検証手順 §2 の共通検査をすべて実行する。
5. 検証手順 §3.3 にこのタスクの行があれば、変更前（`main`）と変更後を同じ機械で続けて測る。
6. 計画書に書かれたコミットメッセージでコミットし、pushし、`main` 向けのPRを作る。マージはしない。

# 守ること

- 統計ID、改訂番号、SaveReader.Version（15）、プロファイルのスキーマ（2）、チェックポイント形式（1）を変えない。
- 既存のテストファイルを編集しない。テストは追加だけ。既存テストが落ちたら、テストではなく自分の変更を直す。
- Unknown（不明）を数値にしない。欠測を0にしない。Partial／Experimental を強い状態に変えない。
- profile.json にある既存のデータを消す変更をしない。
- Source/RimworldStatistics.Api/、README.md、翻訳ファイル（Languages/）を変えない。
- 計画書にない最適化、リネーム、整形、コメントの書き換えをしない。気づいた問題はPR本文の「気づいた点」に書くだけにする。
- リリース、タグ作成、main へのマージ、ワークフローの変更をしない。
- R2（Cloudflare）は読み取りだけ。非公開のセーブ、MOD一覧、ハッシュ値、ファイル名をコミットやPRに書かない。
- 実行していない検査を「通った」と書かない。ゲーム内のTPSや体感速度について何も主張しない。

# 判断に迷ったとき

- 計画書・設計書と実際のコードが食い違っている（行番号がずれている程度は除く。メソッドがない、シグネチャが違う、件数が合わない等）：実装を止め、食い違いの内容をPR本文または報告に書く。推測で進めない。
- 既存テストを変えないと通らない：同上。
- 書かれた期待値（件数、grep の結果）と合わない：原因を調べ、自分の変更の誤りなら直す。計画書の誤りだと判断したら、根拠（実行したコマンドと出力）を添えて報告する。
- 計画書に書かれていない選択（変数名、補助メソッドの置き場所など）：既存コードの書き方に合わせて自分で決めてよい。

# PR本文に書くこと

1. タスク番号と、対応する設計の D 番号、関連 issue 番号（計画書の見出しにある）。
2. 変更したファイルの一覧と、それぞれ何をしたか（1行ずつ）。
3. 共通検査の結果。実行したコマンドと、末尾の出力（テストの total／failed／succeeded／skipped を含む）。省いた検査は「未実行」と理由。
4. 性能比較が要るタスクは、変更前後のハーネス出力の全行と、実行環境（OS、CPUコア数、.NET のバージョン）。
5. 実ゲームでの確認が要るタスク（T6、T8、T9、T11）は、「実ゲームでは未確認」と明記し、検証手順 §4 の該当項目を箇条書きで載せる。
6. 互換性：「統計ID・保存形式・集計結果に変更なし」と書けるか確認して書く。書けない変更があれば、それは計画の範囲外なので取り除く。
7. 気づいた点（任意）。

# タスクごとの注意

- T0：tools/OptimizationBenchmark を追加するだけ。CIのワークフローには足さない。
- T1：変えるのは ColonyIdentity.FingerprintHash() の1メソッドだけ。
- T3：式を移すだけ。条件を「整理」しない。

- T6：登録（設定画面に出る・定義が残る）は従来どおり起動時。遅らせるのは Harmony の Patch 呼び出しだけ。SauAddonStartup.cs と、その既存テストは変えない。

- T10：切り取って貼るだけ。メソッドの中身を1文字も変えない。SaveReader と ProfileMutations で別々のコミットにする。
- T11：所有者の着手指示がなければ実装しない。表示が変わらないことのテスト（計画書 Step 3）を最初に通す。
```

## 所有者向けの補足

- 各PRは小さく、単独で元に戻せるようにしてある。順番に1つずつマージすれば、途中で止めても中途半端な状態にならない。
- T6・T8・T9 はゲーム側の変更で自動テストがない。マージ前に [6 検証手順](2026-11-11-optimization-6-verification.md) §4 の確認を行うことを勧める。
- T11 は、実プロファイルで `profile-report` を実行した結果を見てから決める（[3 優先順位](../specs/2026-11-11-optimization-3-prioritization.md) §2 の条件）。データ保全に関わるので、実装後のレビューは他のタスクより厳しく行うこと。
- 集計の正しさに関わる issue（#112〜#116、#118、#119、#128）はこの計画に含めていない。T3 と T10 が済んでいれば、それらの修正は小さな差分で書ける。
